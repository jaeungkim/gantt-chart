API가 주는 `blockedBy` 목록을 `dependencies`에 그대로 옮기면 화살표가 전부 반대로 나와요. 필드 이름이 `targetId`라서 화살표가 향하는 쪽 작업처럼 읽히거든요. 하지만 그렇지 않아요. 의존성 항목은 후행 작업(successor)에 놓이고, `targetId`에는 그 작업이 기다리는 선행 작업(predecessor)의 id가 들어가요.

## 링크가 놓이는 자리

기다리는 작업 쪽에 항목 하나를 두면 돼요.

```tsx
// src/DependencyExample.tsx
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const tasks: Task[] = [
  {
    id: 'design',
    name: 'Design',
    startDate: '2025-06-02',
    endDate: '2025-06-05',
    parentId: null,
    sequence: '1',
  },
  {
    id: 'build',
    name: 'Build',
    startDate: '2025-06-05',
    endDate: '2025-06-12',
    parentId: null,
    sequence: '2',
    // Build가 Design을 기다리므로 항목은 Build에 놓여요
    dependencies: [{ targetId: 'design', type: 'FS', lag: 2 }],
  },
];

export function DependencyExample() {
  return <ReactGanttChart tasks={tasks} height={300} />;
}
```

이러면 Design에서 Build로 화살표 하나가 그려져요. `design` 자체에는 `dependencies`가 아예 없어요. 필드 타입은 [Task](ref/task)에 정리돼 있어요.

그래프를 만드는 동안 조용히 버려지는 항목이 두 가지 있어요. `targetId`가 그 작업 자신의 id인 의존성, 그리고 `targetId`가 배열의 어떤 작업과도 맞지 않는 의존성이에요.

## 네 가지 타입

두 글자는 링크의 양쪽 끝을 가리켜요. 첫 글자는 선행 작업 쪽 끝이에요. 두 번째 글자는 후행 작업 쪽 끝이고요. `F`는 finish, `S`는 start예요.

| 타입 | 사용하는 선행 작업 끝 | 제약받는 후행 작업 끝 | 링크가 요구하는 날짜 |
|---|---|---|---|
| `FS` | 종료 | 시작 | 후행 작업 시작 = 선행 작업 종료 + lag |
| `SS` | 시작 | 시작 | 후행 작업 시작 = 선행 작업 시작 + lag |
| `FF` | 종료 | 종료 | 후행 작업 종료 = 선행 작업 종료 + lag |
| `SF` | 시작 | 종료 | 후행 작업 종료 = 선행 작업 시작 + lag |

`type`은 모든 항목에 필수예요. 기본값은 없어요.

이 날짜는 링크가 요구하는 값일 뿐, 차트가 알아서 지켜 주는 규칙은 아니에요. `schedulingPolicy`의 기본값은 `off`고, 켜 두더라도 막대를 드래그할 때만 동작해요. 후행 작업을 날짜에 맞춰 앞으로 당길지, 뒤로 미루기만 할지는 정책이 정해요 — [스케줄링](scheduling)을 참고하세요.

`lag: 0`인 `FS` 링크는 선행 작업이 끝나는 바로 그 날짜에 후행 작업이 시작하기를 요구해요. 하루짜리 간격이 암묵적으로 붙는 곳은 어디에도 없어요. 위 예제에서 Design은 06-05에 끝나고 링크에는 `lag: 2`가 있어요. 그래서 링크는 Build 시작을 06-07로 요구해요. 정책을 켠 채 막대를 드래그하기 전까지 Build는 자기 데이터가 준 06-05에 그대로 있어요.

마일스톤에는 자기 종료가 없어요. 마일스톤의 양쪽 끝은 모두 `startDate`로 풀려요. 그래서 마일스톤에서 나가는 `FS` 링크는 `startDate`에 걸려요. 마일스톤 규칙 자체는 [작업 데이터](task-data)에 있어요.

## lag

`lag`은 의존성 항목에 들어가는 부호 있는 정수 일수예요. 양수면 선행 작업의 링크 쪽 끝에서 후행 작업을 그만큼 뒤로 밀어요. 그 끝은 `FS`와 `FF`에서는 종료, `SS`와 `SF`에서는 시작이에요. 음수면 겹쳐요. 다른 도구가 lead라고 부르는 게 이거예요. 별도의 lead 필드는 없어요.

`lag`이 없으면 값을 쓰는 모든 곳에서 `0`으로 읽혀요.

단위는 현재 달력이 세는 하루예요. 기본은 달력 일수고, `workingCalendar`를 켜면 근무일이 돼요 — [스케줄링](scheduling)을 참고하세요. 값을 쓰는 모든 지점이 정수 일수로 다루기 때문에 소수점 `lag`은 의미가 없어요.

> [!IMPORTANT]
> `lag`은 입력 전용 데이터예요. 차트에서 그린 링크는 `lag` 키 없이 `{ targetId, type }`으로 기록돼요. 이미 있는 링크의 lag을 바꾸는 제스처나 키, 콜백도 없어요. 값을 바꾸려면 직접 들고 있는 `tasks` 배열에서 항목을 다시 써야 해요.

## 링크 그리기

막대마다 양쪽 끝에 연결 점이 하나씩, 두 개 달려 있어요. 10px 원이고, 작업 막대에서는 `left: -14px`와 `right: -14px`에 놓여요. 마일스톤에서는 `left: -9px`와 `left: 15px`에 놓여서 마름모의 좌우 꼭짓점에 자리해요. 막대에 호버하거나 막대를 선택하기 전까지는 투명해요. 그리고 그 작업의 `canCreateLink`가 true로 풀릴 때만 렌더링돼요.

점에서 드래그해 다른 막대 위에서 놓으면 돼요. 타입은 양쪽 앵커에서 정해져요.

| 드래그 시작 지점 | 놓는 위치 | 타입 |
|---|---|---|
| 선행 작업의 끝 점 | 후행 작업의 왼쪽 절반 | `FS` |
| 선행 작업의 시작 점 | 후행 작업의 왼쪽 절반 | `SS` |
| 선행 작업의 끝 점 | 후행 작업의 오른쪽 절반 | `FF` |
| 선행 작업의 시작 점 | 후행 작업의 오른쪽 절반 | `SF` |

어느 쪽 절반인지는 대상 박스의 가로 중점으로 정해져요. 마일스톤에서 재는 박스는 라벨까지 감싸는 래퍼가 아니라 마름모예요. 드롭 대상은 `elementFromPoint`로 찾아요. 그래서 가장 가까운 막대가 아니라 포인터 바로 아래에 있는 막대 요소가 대상이 돼요.

`Escape`를 누르면 드래그가 취소돼요.

### 드래그가 거부하는 것

포인터가 후보 위에 있는 동안 차트는 두 작업의 짝을 검사해요. 거부된 대상은 빨갛게 변하고, 이유가 포인터 옆에 그려져요. 그 상태로 놓아도 아무것도 반영되지 않아요.

| 거부 | 조건 | 표시되는 문구 |
|---|---|---|
| 자기 참조 | 두 id가 같음 | `Cannot link a task to itself` |
| 중복 | 후행 작업에 이 선행 작업을 가리키는 항목이 이미 있음 | `These tasks are already linked` |
| 순환 | 선행 작업의 선행 작업들을 따라가면 후행 작업에 닿음 | `That would create a circular dependency` |

순서는 고정이에요. 자기 참조, 그다음 중복, 그다음 순환이에요.

중복 검사는 `targetId`만 비교해요. `type`은 무시하죠. 그래서 `design → build` 링크가 어떤 타입으로든 이미 있으면 같은 방향의 두 번째 링크는 거부돼요. 반대 방향 짝은 별개의 문제고, 순환 규칙이 따로 검사해요.

세 문구는 영어로 하드코딩돼 있어요. `locale`이나 `formats`를 거치지 않아요.

`canCreateLink`가 false인 대상은 더 일찍, 더 조용하게 거부돼요. 강조도 되지 않고, 이유 문구도 뜨지 않고, 놓아도 아무 일이 없어요.

### onDependencyCreate에 도달하는 것

드래그가 거부하지 않은 것 전부예요. 그룹이나 레인을 가로지르는 링크, 요약 행으로 향하는 링크, 마일스톤을 오가는 링크, 스케줄러가 결코 만족시킬 수 없는 링크까지 모두 콜백에 도착해요.

```tsx
// src/LinkGuard.tsx
import { useState } from 'react';
import {
  ReactGanttChart,
  type GanttDependencyChange,
  type Task,
} from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

export function LinkGuard({ initial }: { initial: Task[] }) {
  const [tasks, setTasks] = useState<Task[]>(initial);

  return (
    <ReactGanttChart
      tasks={tasks}
      onTasksChange={setTasks}
      onDependencyCreate={(change: GanttDependencyChange) => {
        // 정확히 false일 때만 중단돼요
        if (change.type === 'SF') return false;
      }}
      onDependencyDelete={({ predecessorId, successorId }) =>
        window.confirm(`Unlink ${predecessorId} -> ${successorId}?`)
      }
    />
  );
}
```

반환값은 `=== false`로 비교돼요. `true`, `undefined`, `null`, `0`은 모두 반영돼요. Promise도 마찬가지예요. 이 두 콜백은 동기 전용이라 반환된 Promise를 기다리지 않아요. 그래서 비동기 가드는 링크가 이미 데이터에 들어간 뒤에 resolve돼요. `onBeforeTaskChange`는 await해요. 기다려 주는 핸들러는 [이벤트와 취소 가능한 변경](events)에서 확인하세요.

`GanttDependencyChange`는 `predecessorId`, `successorId`, `type`만 담고 그 외에는 없어요. 어느 방향으로도 `lag`은 없어요. 구조는 [변경과 초안 타입](ref/changes)에 있어요.

반영된 링크는 되돌리기 한 단계예요. [명령형 API](imperative-api)로 되돌릴 수 있어요.

## 링크 삭제

화살표마다 경로를 따라 12px 폭의 보이지 않는 히트 패스가 있어요. 후행 작업의 `canDeleteLink`가 true일 때만 그려져요. 여기에 포인터를 누르면 화살표가 선택돼요. 선택된 화살표는 강조 색으로 바뀌고, 양 끝점의 중간에 원 안에 X가 든 둥근 삭제 버튼이 생겨요.

화살표가 하나 선택돼 있는 동안에는 이렇게 동작해요.

| 입력 | 동작 |
|---|---|
| `Delete` 또는 `Backspace` | 선택된 링크를 삭제해요 |
| `Escape` | 선택을 해제해요 |
| 아무 곳에서나 포인터 누르기 | 선택을 해제해요 |

포커스가 `input`, `textarea`, `select`, `contentEditable` 요소에 있으면 키 입력은 무시돼요.

권한은 후행 작업의 `canDeleteLink`를 읽어요. `dependencies` 배열에서 항목이 빠지는 쪽 작업이죠. 선행 작업에 `allowLinkDelete: false`를 줘도 달라지는 건 없어요. 플래그가 false면 삭제는 조용히 반환돼요.

삭제는 `targetId`만으로 걸러 내요. 한 후행 작업에 같은 선행 작업을 가리키는 항목이 둘 있으면 화살표 두 개가 함께 선택돼요. 그리고 한 번의 삭제로 둘 다 사라져요.

막대 셀에 키보드 포커스가 있고 화살표도 선택돼 있으면 `Delete`가 두 핸들러에 동시에 닿아요. 링크가 지워지고 포커스된 작업도 삭제되며, 되돌리기 단계는 둘로 나뉘어요. 작업 삭제 키는 [키보드와 스크린 리더](accessibility)에 정리돼 있어요.

## 상호작용 함정

작업에 `allowLinkCreate: false`를 주면 양방향이 모두 막혀요. 점을 렌더링할 때 출발 쪽에서 한 번 읽고, 드래그 중에 드롭 대상에서 또 읽어요. 그래서 그 작업은 링크를 시작할 수도, 받을 수도 없어요. 이 플래그들의 전체 해석 순서 — 작업 플래그, `task.readOnly`, 차트 prop, 차트 `readOnly` — 는 [작업 편집](editing)에 있어요.

`renderBar`를 쓰면 그 막대의 링크 편집이 꺼져요. 커스텀 노드는 `style`, `onPointerDown`, `onClick`, `onDoubleClick`만 든 `barProps`를 받아요. 연결 점도 없고 `data-task-id`도 없어요. 드롭 감지는 `data-task-id`를 찾기 때문에 그 막대는 드래그를 시작할 수도, 드롭 대상이 될 수도 없어요. `barProps`를 펼쳐 넣어도 의존성은 돌아오지 않고, 경고도 뜨지 않아요. [커스텀 렌더링](custom-rendering)을 참고하세요.

데이터에 순환이 이미 있으면 그 탐색에서는 순환 가드가 동작하지 않아요. 가드는 한 번 본 id를 다시 방문하지 않아요. 그래서 탐색이 후행 작업에 닿기 전에 기존 순환에서 멈추고, 새 링크가 그대로 통과해요.

링크를 만들거나 지워도 일정은 다시 계산되지 않아요. `schedulingPolicy`는 막대 드래그에서만 동작해요. 그래서 새 `FS` 링크를 걸어도 겹쳐 있던 후행 작업은 있던 자리에 그대로 남아요 — [스케줄링](scheduling)을 참고하세요.

## 링크를 직접 검사하기

`canLink(tasks, predecessorId, successorId)`는 `{ ok, cycle }`을 반환해요. 자기 참조와 순환은 거부하지만 중복은 거부하지 않아요. 그래서 드래그가 쓰는 가드와 같지 않아요.

`linkKey(link)`는 링크 하나를 식별하는 `"design>build:FS"` 문자열을 만들어요. `criticalLinkIds`가 쓰는 키 형식이 이거예요.

둘 다 패키지에서 export되고 [작업 그래프 헬퍼](ref/core-graph)에 정리돼 있어요.

## 한계

차트는 링크를 그리고 지워요. 관리하지는 않아요.

- **lag 편집 없음.** `lag`을 기록하는 핸들, 다이얼로그, 키, 콜백이 없어요. UI에서 그린 링크에는 항상 lag이 없어요.
- **타입 편집 없음.** 화살표가 생긴 뒤에 `FS`를 `SS`로 바꾸려면 `tasks` 배열의 항목을 다시 써야 해요.
- **생성 시 적용 없음.** `FS` 링크를 추가해도 후행 작업은 움직이지 않고, 날짜를 검사하는 곳도 없어요. 링크는 막대 드래그에서만, 그리고 `schedulingPolicy`가 기본값 `off`에서 벗어나야만 적용돼요.
- **링크로 가는 키보드 경로 없음.** 연결 점은 `tabIndex={-1}`을 달고 있고, 링크 드래그를 시작하는 키도 없어요. `Delete`가 통하려면 먼저 포인터로 화살표를 선택해야 해요.
- **다중 선택 없음.** 화살표는 한 번에 하나만 선택돼요.
- **화살표의 호버 툴팁, 컨텍스트 메뉴, 라벨 없음.** 쓸 수 있는 건 히트 패스와 선택된 화살표의 삭제 버튼뿐이에요.
- **호버나 선택 없이는 점도 없음.** 손가락에는 호버가 없어서 터치 사용자는 막대를 먼저 선택해야 해요. 선택 자체도 `selectable`이나 `onTaskSelect`를 주기 전까지는 꺼져 있어요. 둘 중 하나가 없으면 터치 사용자는 점에 영영 닿지 못해요.
- **화살표 경로 재조정 없음.** 꺾임은 양 끝점과 타입만으로 계산돼요. 그래서 화살표가 막대를 거리낌 없이 가로질러요.
- **숨은 작업으로 가는 화살표 없음.** 선행 작업이 필터로 빠졌거나 접힌 부모 아래 숨어 있으면 링크는 그려지지 않아요. 그래도 링크는 존재하고 일정도 계속 제약해요.
- **알 수 없는 `type` 값은 사라짐.** `'fs'` 같은 오타는 화살표를 만들지 않아요. 유일한 진단은 개발 모드에서만 나오는 `console.warn`이고, 서로 다른 잘못된 값마다 한 번씩 찍혀요.
- **"링크 수정" 콜백 없음.** `onDependencyCreate`와 `onDependencyDelete`가 있을 뿐, 그 사이는 없어요.
- **드래그의 가드는 내부용.** 차트가 쓰는 함수는 호스트 앱에서 import할 수 없어요. `canLink`가 공개된 근사치인데 중복은 놓쳐요.
- **`linkKey`는 `lag`을 무시함.** 같은 짝에 같은 `type`, 다른 `lag`을 가진 항목 둘은 같은 키를 만들어요. 그래서 `criticalLinkIds`는 둘을 구분하지 못해요.

다음: [스케줄링](scheduling) — 막대가 움직인 뒤 차트가 이 링크들로 무엇을 하는지 다뤄요.
