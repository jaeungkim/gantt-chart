세 팀에서 온 작업 마흔 개가 평평한 목록 하나로 도착해요. 이걸 읽으려면 회의에서 누군가 정한
접두사를 이름 열에서 눈으로 훑어야 해요. `groupBy`는 그 목록을 헤더 행이 하나씩 달린 밴드로
나눠요. 그리고 작업 필드 `lane`은 서로 겹치지 않는 작업을 한 행에 모아요.

<GanttDemo preset="grouping" />

둘은 서로 독립적이에요. 그룹은 작업이 어느 밴드에 앉을지 정해요. 레인은 그 밴드에 행이 몇 개
필요한지 정해요.

## 필드로 그룹 묶기

`groupBy`는 필드 이름이나 접근자(accessor)를 받아요.

```tsx
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';

// 문자열 형태는 인덱스 접근으로 작업에서 필드를 그냥 읽어요. 그러니 `any`로 도망가지 말고
// 직접 정의한 작업 타입을 넓혀 주세요.
type ProjectTask = Task & { team?: string | null };

const tasks: ProjectTask[] = [
  { id: 'spec', name: 'Spec', team: 'Design', parentId: null, sequence: '1',
    startDate: '2026-03-02T00:00:00Z', endDate: '2026-03-06T00:00:00Z' },
  { id: 'api', name: 'API', team: 'Backend', parentId: null, sequence: '2',
    startDate: '2026-03-02T00:00:00Z', endDate: '2026-03-13T00:00:00Z' },
];

export function TeamChart() {
  return <ReactGanttChart tasks={tasks} groupBy="team" height={480} />;
}
```

접근자 형태는 변환된 작업을 받아서 그룹 값을 돌려줘요.

```tsx
import {
  ReactGanttChart,
  type Task,
  type TaskTransformed,
} from '@jaeungkim/gantt-chart';

function byMonth(task: TaskTransformed): string | null {
  if (task.type === 'milestone') return null; // 마일스톤은 Ungrouped로 떨어져요
  return task.startDate.slice(0, 7); // "2026-03"
}

export function MonthChart({ tasks }: { tasks: Task[] }) {
  return <ReactGanttChart tasks={tasks} groupBy={byMonth} height={480} />;
}
```

전체 시그니처는 `string | ((task: TaskTransformed) => string | null | undefined)`이에요. 반환
타입에 있는 `null`과 `undefined`는 그냥 붙어 있는 게 아니에요. 접근자가 "이 작업은 그룹이
없다"고 말하는 방법이에요. 인자는 원본 `Task`가 아니라 `TaskTransformed`예요. 그래서 접근자는
`depth`, `order`, `isSummary`, 막대 위치, 그리고 해당 prop이 켜져 있을 때의 스케줄링 지표까지
볼 수 있어요 — [Task](ref/task) 참고.

`null`, `undefined`, `""`이 아닌 모든 값은 `String(value)`를 거쳐요. 그 문자열이 그룹 키이면서
동시에 헤더 라벨이에요. 라벨을 따로 만드는 콜백은 없어요.

그룹 순서는 작업 배열에서 처음 등장한 순서, 곧 `sequence` 순서예요 —
[작업 데이터](task-data) 참고. 그룹을 정렬하는 prop은 없어요. 작업이 하나도 없는 그룹을
선언하는 prop도 없어요. 그룹은 거기 들어간 작업이 있어서 존재해요.

문자열 형태는 검사 없는 인덱스 읽기예요. `owner`가 없는 작업에 `groupBy="owner"`를 줘도 오류가
나지 않아요. 모든 작업이 Ungrouped 밴드 하나로 떨어져요.

## Ungrouped 버킷

작업을 Ungrouped 버킷에 넣는 값은 정확히 세 개예요. `null`, `undefined`, 그리고 빈 문자열이에요.
나머지 값은 전부 자기만의 그룹이 돼요.

| 필드 또는 접근자 값 | 그룹 키 | 헤더 라벨 |
|---|---|---|
| `"Design"` | `"Design"` | `Design` |
| `null` | `""` | `ungroupedLabel` |
| `undefined` | `""` | `ungroupedLabel` |
| `""` | `""` | `ungroupedLabel` |
| `0` | `"0"` | `0` |
| `false` | `"false"` | `false` |
| `NaN` | `"NaN"` | `NaN` |

표 아래쪽 절반의 falsy 값 세 개는 특별 취급을 받지 않아요. `progress: 0`인 작업에
`groupBy="progress"`를 주면 헤더가 `0`인 밴드가 생겨요. 헤더가 `40`인 밴드 바로 옆에요.

`ungroupedLabel`로 그 밴드 이름을 바꿔요. 기본값은 `"Ungrouped"`이고, 이 기본값은 prop 단계가
아니라 행 빌더 안에서 적용돼요.

```tsx
<ReactGanttChart tasks={tasks} groupBy="team" ungroupedLabel="No team" />
```

그래서 `ungroupedLabel=""`을 넘기면 기본값이 아니라 빈 헤더가 나와요. 빈 문자열도 넘겨준
값이라 폴백이 아예 동작하지 않아요. 헤더 행은 개수 배지 하나만 단 채 원래 높이 그대로
렌더링돼요.

> [!IMPORTANT]
> Ungrouped 밴드의 접기 id는 글자 그대로 `"group:"`이에요. 접두사 뒤에 빈 키가 붙은 모양이죠.
> 이 id는 그룹 키로 만들어지는데, 그 키가 `""`이기 때문이에요. 라벨은 전혀 관여하지 않아요.
> 그래서 `collapsedIds={['group:Ungrouped']}`는 조용히 아무 일도 하지 않아요.

## 그룹 헤더 행

그룹 헤더는 작업 행과 같은 목록에 들어 있는 진짜 행이에요. 행 사이에 그려 넣은 장식이 아니에요.

| 속성 | 값 |
|---|---|
| 행 위의 작업 | 없음 |
| depth / `aria-level` | `0` / `1` |
| 행 id | `` `group:${key}` `` |
| 높이 | 38px, 다른 모든 행과 같아요 |
| `aria-rowcount`에 포함 | 예 |
| PNG 내보내기의 행 수에 포함 | 예 |
| 키보드 셀 | 1 — 헤더 전체가 셀 하나 |

배지의 숫자는 차트가 받은 작업 중 그 그룹에 속한 작업 수예요. 눈에 보이는 집합이 기준이라,
그룹 안의 요약 행을 접으면 배지 숫자가 줄어요. 그룹 자체를 접으면 숫자는 그대로예요. 접기가
적용되기 전에 개수를 세기 때문이에요.

### 그룹 접기

그룹 헤더는 요약 행과 같은 접기 상태를 써요. [작업 목록과 계층](task-list)에 정리된
`collapsedIds` / `defaultCollapsedIds` / `onCollapsedChange` 세 가지예요. 평평한 문자열 목록
하나가 두 종류의 id를 함께 담아요. 그룹 처리 단계는 작업 id를 무시하고, 트리 필터는 `group:`
id를 무시해요. 그래서 둘이 부딪힐 일은 없어요.

```tsx
// Backend 밴드와 Ungrouped 밴드를 접은 채로 시작해요.
<ReactGanttChart
  tasks={tasks}
  groupBy="team"
  defaultCollapsedIds={['group:Backend', 'group:']}
/>
```

접힌 그룹은 헤더는 남기고 멤버 행은 빼요. 키는 이스케이프 없이 그대로 쓰여요. 그래서
`:`나 `+`가 들어간 그룹 값은 id에도 그 모습 그대로 나타나요.

그룹 접기는 `hierarchy`가 켜져 있든 꺼져 있든 동작해요. 두 접기 방식은 별개의 코드 경로예요.

`showTaskList`가 꺼져 있으면 헤더 행에 펼침 버튼이 없어요. 타임라인 패널은 라벨과 개수만
그려요. 그래서 밴드를 키보드로는 접을 수 있지만 포인터로는 접을 수 없어요 —
[키보드와 스크린 리더](accessibility) 참고.

### 헤더 스타일 주기

| 선택자 | 무엇인지 |
|---|---|
| `.gantt-grid-row.group` | 작업 목록의 헤더 행 |
| `.gantt-task-row.group` | 타임라인의 헤더 행 |
| `.gantt-group-label` | 라벨. `position: sticky; left: 0`이라 가로 스크롤에도 살아남아요 |
| `.gantt-grid-group-count` | 개수 알약. 레인의 `+N` 배지에도 같이 쓰여요 |

색은 [테마](theming)의 `--gantt-*` 커스텀 속성에서 와요.

## 그룹과 parentId 계층

그룹은 가장 바깥 단계를 차지해요. 헤더는 언제나 depth 0이고, 밴드 안의 작업 행은 한 단계 더
깊어요. 그리고 모든 헤더는 서로 형제예요. 중첩은 없어요. `groupBy` 값은 하나뿐이고, 목록이
아니에요.

그룹으로 묶인 작업 행은 depth 1 이상에 앉아요. 그래서 `hierarchy`가 꺼져 있어도 `groupBy`를
켜면 모든 작업 행이 16px 들여쓰기돼요.

`hierarchy`가 켜져 있으면 작업의 그룹은 작업 자신이 아니라 **최상위 조상**에서 읽어요. 그래서
서브트리가 두 밴드로 쪼개지는 일은 없어요. 부모와 자식의 필드 값이 아무리 달라도요. `name`으로
묶을 때, `Dev`라는 부모 아래의 `QA`라는 자식은 `Dev`에 들어가요.

단계는 하나씩 밀려요. 헤더가 `aria-level` 1, 루트 작업이 2, 그 자식이 3이에요.

`hierarchy`가 꺼져 있으면 최상위 조상을 찾는 과정 자체가 없어요. 그룹은 작업 자신에서 나오고
`parentId`는 무시돼요. 최상위 조상 규칙과 `hierarchy` prop은 같은 스위치예요 —
[작업 목록과 계층](task-list) 참고.

## 레인

`lane`은 차트 prop이 아니라 작업의 필드예요. 같은 그룹 안에서 lane 문자열이 같은 작업들은 한
행에 나란히 그려져요.

```tsx
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';

const tasks: Task[] = [
  { id: 'spec', name: 'Spec', lane: 'ana', parentId: null, sequence: '1',
    startDate: '2026-03-02T00:00:00Z', endDate: '2026-03-06T00:00:00Z' },
  { id: 'wires', name: 'Wireframes', lane: 'ana', parentId: null, sequence: '2',
    startDate: '2026-03-09T00:00:00Z', endDate: '2026-03-12T00:00:00Z' },
];

<ReactGanttChart tasks={tasks} height={480} />;
```

falsy한 `lane`은 레인이 없는 것과 같아요. `lane: ""`은 필드를 생략했을 때처럼 작업에 자기 행을
하나 줘요.

### 레인 패킹이 동작하는 방식

레인 멤버는 시작 날짜 순서대로, 먼저 맞는 행에 그리디하게 채워져요.

| 규칙 | 효과 |
|---|---|
| 정렬 | 입력 순서가 아니라 `startDate` 기준이에요. 시작이 같으면 입력 순서를 지켜요 |
| 배치 | 가장 빈틈없는 행이 아니라, 마지막 막대가 이미 끝난 **첫** 행에 들어가요 |
| 맞닿음 | 앞 막대가 끝나는 시점에 정확히 시작하는 작업은 같은 행을 써요 |
| 겹침 | 겹치는 작업은 행을 하나 더 열어요 |
| 재사용 | 행은 비는 즉시 다시 쓰여요 |
| 마일스톤 | `startDate`만 차지하고 `endDate`는 무시돼요 |

패킹은 그룹마다 따로 돌아요. 다른 그룹에 있는 같은 lane 문자열의 두 작업은 절대 한 행을 쓰지
않아요. 묶인 행들은 그 레인에서 처음 등장한 멤버의 자리에 들어가요. 뒤에 오는 멤버는 자기
자리에 아무것도 남기지 않아요.

작업 목록에서 레인 행은 **가장 먼저 시작하는** 작업의 열을 보여줘요. 입력 배열의 첫 작업이
아니라 패킹이 끝난 뒤의 `tasks[0]`이에요. 여기에 첫 열의 `+N` 배지가 붙는데, N은 같은 행에 있는
다른 작업의 수예요.

### 레인 행이 치르는 대가

레인 행 위의 모든 작업은 같은 `order`를 보고해요. `order`는 의존성 화살표의 세로 위치를
정해요. 그래서 같은 레인 행에 있는 두 작업 사이의 연결은 수평선 하나로 그려져요 —
[의존성](dependencies) 참고.

레인 행 위에 새 작업을 그리면 `rowTaskId`로는 가장 먼저 시작하는 작업의 id만 넘어와요. 나머지
멤버는 그 방법으로는 닿을 수 없어요. 그룹 헤더 행 위에 그리는 건 막혀 있지 않고,
`rowTaskId: null`을 넘겨요 — [작업 편집](editing) 참고.

> [!WARNING]
> 그룹 헤더가 하나라도 생기거나 레인 행 하나가 작업 두 개를 담는 순간, 행 재정렬이 조용히,
> 그리고 차트 전체에서 스스로 꺼져요. 행 id가 곧 작업 id인 건 모든 행이 정확히 작업 하나만
> 담을 때뿐이에요. 경고도 콜백도 없이 행이 그냥 끌리지 않게 돼요. `groupBy`와
> `allowRowReorder`는 사실상 같이 쓸 수 없어요 — [행 재정렬](reordering) 참고.

레인 안에서 파싱할 수 없는 `endDate`는 그 작업이 연 행을 오염시켜요. 배치 검사는
`rowEnd <= start`인데, `NaN`과의 비교는 전부 false예요. 그래서 그 행은 다시는 뒤 작업에게
제안되지 않아요. 뒤따르는 레인 멤버는 다음 빈 행으로 밀려가고, 빈 행이 없으면 새 행을 열어요.

## 예제로 따라가 보기

`team`으로 묶은 작업 다섯 개예요. 그중 셋은 `ana` 레인을 함께 써요. `hierarchy`는 꺼져 있어요.

```tsx
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';

type ProjectTask = Task & { team?: string | null };

const tasks: ProjectTask[] = [
  { id: 'spec', name: 'Spec', team: 'Design', lane: 'ana', parentId: null, sequence: '1',
    startDate: '2026-03-02T00:00:00Z', endDate: '2026-03-06T00:00:00Z' },
  { id: 'wires', name: 'Wireframes', team: 'Design', lane: 'ana', parentId: null, sequence: '2',
    startDate: '2026-03-09T00:00:00Z', endDate: '2026-03-12T00:00:00Z' },
  { id: 'review', name: 'Review', team: 'Design', lane: 'ana', parentId: null, sequence: '3',
    startDate: '2026-03-04T00:00:00Z', endDate: '2026-03-05T00:00:00Z' },
  { id: 'api', name: 'API', team: 'Backend', parentId: null, sequence: '4',
    startDate: '2026-03-02T00:00:00Z', endDate: '2026-03-13T00:00:00Z' },
  { id: 'cleanup', name: 'Cleanup', team: null, parentId: null, sequence: '5',
    startDate: '2026-03-16T00:00:00Z', endDate: '2026-03-18T00:00:00Z' },
];

<ReactGanttChart tasks={tasks} groupBy="team" height={480} />;
```

작업 다섯 개에서 행 일곱 개가 나와요.

```text
task list                       timeline
                                Mar 2      Mar 9      Mar 16
────────────────────────────────────────────────────────────
v Design                 3
    Spec            +1          [ Spec  ]  [ Wires  ]
    Review                        [Rev]
v Backend                1
    API                         [      API      ]
v Ungrouped              1
    Cleanup                                        [Cleanup]
```

| 행 | `id` | depth | 행 위 작업의 `order` |
|---|---|---|---|
| 1 | `group:Design` | 0 | — |
| 2 | `spec+wires` | 1 | 둘 다 `2` |
| 3 | `review` | 1 | `3` |
| 4 | `group:Backend` | 0 | — |
| 5 | `api` | 1 | `5` |
| 6 | `group:` | 0 | — |
| 7 | `cleanup` | 1 | `7` |

이 표에서 잠깐 멈춰 볼 대목이 셋 있어요. `spec`은 3월 6일에 끝나고 `wires`는 3월 9일에
시작해서 둘이 2행을 함께 써요. `review`는 `spec`과 겹치니까 3행을 열어요. 헤더 행도 `order`
번호를 하나씩 소비해요. 그래서 `api`가 `3`이 아니라 `5`를 보고해요. Ungrouped 헤더의 id는
`group:`이고, 라벨은 `Ungrouped`예요.

## 한계

그룹은 `order`만 다시 쓰고 나머지는 건드리지 않아요. 날짜도, 막대 위치도, `originalOrder`도
그대로예요.

이 영역이 하지 않는 일이에요.

- **정렬 없음.** 그룹 순서는 작업 배열에서 처음 등장한 순서예요. 밴드 순서를 바꾸려면 작업
  순서를 바꿔야 해요.
- **빈 그룹 없음.** 작업이 없는 밴드는 렌더링되지 않아요. "이 그룹들은 항상 보여 줘" 같은
  옵션은 없어요.
- **중첩 없음.** `groupBy`는 값 하나예요. 헤더는 언제나 depth 0이에요.
- **그룹을 가로지르는 레인 없음.** 패킹은 밴드마다 돌아요. 그래서 lane 문자열 하나가 여러
  밴드에서 행을 만들 수 있어요.
- **검증 없음.** 없는 필드 이름은 오류 대신 Ungrouped 밴드 하나를 내놓아요.
- **저장 없음.** 접힌 그룹 id는 다른 접힌 행과 똑같이 `collapsedIds`에 들어 있어요.
- **객체 동일성 보장 없음.** 행 번호가 바뀐 작업은 얕은 복사본으로 넘어가요. 그래서 `groupBy`를
  켜면 차트가 렌더러와 콜백에 넘기는 작업 참조가 거의 전부 바뀌어요. 그룹도 레인도 없는 차트는
  받은 객체를 그대로 돌려줘요.
- **작업 목록에서는 레인 행마다 작업 하나.** 레인 행의 열과 키보드 셀은 가장 먼저 시작하는
  작업만 건드려요. 나머지 멤버는 자기 막대로만 닿을 수 있어요 —
  [키보드와 스크린 리더](accessibility) 참고.
- **내보내는 헬퍼 없음.** 행 빌더, 레인 패커, `group:` 접두사는 전부 내부 구현이에요. 밖으로
  나가는 건 `GanttGroupBy`, `GanttRow`, `GanttRowGroup` 타입뿐이에요 —
  [그룹 타입](ref/grouping) 참고.

호스트 앱이 직접 해야 하는 일이에요.

- `collapsedIds`를 초기화하거나 제어할 때 `group:` id 문자열을 손으로 만들기. 패키지는 접두사도
  헬퍼도 내보내지 않아요.
- 헤더 행 위에 그리는 게 가능한 상황이라면 `onTaskCreate`에서 `rowTaskId: null` 처리하기.
- `groupBy`를 쓸 때는 `allowRowReorder`를 끄거나, 그게 없는 전제로 설계하기.
- 작업 순서를 정해서 밴드 순서 정하기.
- `groupBy`의 문자열 형태가 읽는 필드를 직접 정의한 작업 타입에 추가하기.
