한 문서에서 `row`를 읽고 다음 문서에서 `task`를 읽으면, 둘을 같은 것으로 넘겨짚게 돼요. 둘은 같지
않고, 그 차이는 작업 두 개가 한 행을 공유하는 순간 바로 문제가 돼요. 이 문서에서 하나의 대상에 하나의
단어를 못 박을게요. 나머지 문서는 모두 이 단어만, 오직 이 단어만 써요.

## 차트와 호스트 앱

**차트**는 `@jaeungkim/gantt-chart`가 내보내는 `<ReactGanttChart>` 컴포넌트예요. `tasks` prop이 준
것을 그리고, 모든 편집을 다시 알려줘요.

**호스트 앱**은 그 주변을 감싸는 애플리케이션이에요. 작업 배열을 소유하고, 무엇을 저장할지 정하고,
차트가 `onTasksChange`로 넘긴 것을 반영해요 — [이벤트와 변경 취소](events)를 참고해요.

## 화면에 있는 것

```text
        task list                                  timeline
┌──────────────────────────┬───────────────────────────────────────────────┐
│                          │  March 2026                  │  April 2026    │  top header row
│                          │  2    9    16   23   30      │  6    13       │  ticks (one per day; thinned to fit)
├──────────────────────────┼───────────────────────────────────────────────┤
│ ▾ Phase 1                │  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓                      │  summary row
│     Design         +1    │  ████──▶ ███████████████                      │  lane row: two tasks
│                          │          ▁▁▁▁▁▁▁▁▁▁▁▁▁                        │  baseline, same row
│   Ship                   │                          ◆                    │  milestone
└──────────────────────────┴───────────────────────────────────────────────┘
```

| 단어 | 가리키는 것 |
|---|---|
| 작업(task) | 데이터 한 건이에요. `tasks` 배열의 항목 하나를 말해요. |
| 막대(bar) | 작업 하나를 위해 그려지는 가로 블록이에요. 이걸 끌어 옮기는 건 [작업 편집](editing)이에요. |
| 행(row) | 그리드의 한 줄이에요. 작업을 0개, 1개, 또는 여러 개 담을 수 있어요. |
| 작업 목록(task list) | 왼쪽 패널이에요. 타임라인 옆에 놓인 컬럼 그리드를 말해요. [작업 목록과 계층](task-list)을 참고해요. |
| 타임라인(timeline) | 시간 축과 그 위에 그려지는 모든 것이에요. [타임라인](timeline)을 참고해요. |
| 배율(scale) | 타임라인을 그리는 단위예요. `hour`, `day`, `week`, `month`, `quarter`, `year` 중 하나예요. [타임라인](timeline)을 참고해요. |
| 눈금(tick) | 아래쪽 헤더 행의 칸 하나예요. 눈금 하나가 덮는 시간은 배율에 따라 달라져요. |
| 요약 행(summary row) | `parentId`로 자식을 가진 작업이고, `hierarchy`가 켜져 있을 때예요. 날짜는 자식에게서 와요. [작업 목록과 계층](task-list)을 참고해요. |
| 마일스톤(milestone) | `type: 'milestone'`인 작업이에요. `startDate` 위치에 마름모로 그려져요. [작업 데이터](task-data)를 참고해요. |
| 그룹 헤더 행(group header row) | 적어도 한 작업이 가진 `groupBy` 값이 만들어 내는 밴드 라벨이에요. 자기 작업은 갖지 않아요. [그룹과 스윔레인](grouping)을 참고해요. |
| 스윔레인(swimlane) | 그룹 헤더 행 하나 아래에 묶인 행 밴드예요. [그룹과 스윔레인](grouping)을 참고해요. |
| 레인(lane) | `lane` 필드예요. 여러 작업을 한 행에 나란히 놓아요. [그룹과 스윔레인](grouping)을 참고해요. |

위의 모든 단어는 이 스니펫 안의 무언가를 가리켜요.

```tsx
// concepts-demo.tsx
import { useState } from 'react';
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const initialTasks: Task[] = [
  {
    id: 'phase-1',
    name: 'Phase 1',
    startDate: '2026-03-02',
    endDate: '2026-03-20',
    parentId: null,
    sequence: '1',
  },
  {
    id: 'design',
    name: 'Design',
    startDate: '2026-03-02',
    endDate: '2026-03-06',
    parentId: 'phase-1',
    sequence: '1.1',
    lane: 'Ana',
  },
  {
    id: 'build',
    name: 'Build',
    startDate: '2026-03-09',
    endDate: '2026-03-20',
    parentId: 'phase-1',
    sequence: '1.2',
    lane: 'Ana',
    progress: 40,
    dependencies: [{ targetId: 'design', type: 'FS', lag: 1 }],
    baselineStart: '2026-03-09',
    baselineEnd: '2026-03-18',
  },
  {
    id: 'ship',
    name: 'Ship',
    type: 'milestone',
    startDate: '2026-03-23',
    endDate: '2026-03-23',
    parentId: null,
    sequence: '2',
    dependencies: [{ targetId: 'build', type: 'FS' }],
  },
];

export function Demo() {
  const [tasks, setTasks] = useState<Task[]>(initialTasks);

  return (
    <ReactGanttChart
      tasks={tasks}
      onTasksChange={setTasks}
      hierarchy
      workingCalendar
      criticalPath
    />
  );
}
```

작업 네 개, 행 세 개예요. `design`과 `build`는 `Ana` 레인을 공유하면서 시간이 겹치지 않아요. 그래서
한 행에 함께 담겨요. 그 묶는 규칙은 [그룹과 스윔레인](grouping)이 소유해요.

## 데이터를 가리키는 단어

**작업(Task).** 직접 넘기는 단위예요. 필수 필드는 `id`, `name`, `startDate`, `endDate`, `parentId`,
`sequence` 여섯 개고, 나머지는 선택이에요. 필드 표는 [작업 데이터](task-data)에, 타입은
[`Task`](ref/task)에 있어요.

**마일스톤(milestone).** `type`이 정확히 `'milestone'` 문자열인 작업이에요. `startDate` 위치에
마름모로 그려지고, `endDate`는 렌더링, 롤업, 레인 패킹, 일정 계산에서 무시돼요. 다만 타임라인이 자기
날짜 범위를 계산할 때는 여전히 읽혀요. 그래서 마일스톤에 엉뚱한 `endDate`가 남아 있으면 아무것도
그려지지 않은 채 차트만 늘어나요. 이 필드가 여전히 영향을 주는 자리는 [작업 데이터](task-data)가
모두 나열해요.

**의존성(dependency).** 작업 두 개를 잇는 링크예요. 타입은 `FS`, `SS`, `FF`, `SF` 네 가지예요. 첫
글자는 선행 작업(predecessor)의 끝점, 둘째 글자는 후행 작업(successor)의 끝점이에요.
[의존성](dependencies)을 참고해요.

**선행 작업과 후행 작업.** 선행 작업은 링크에서 앞선 작업, 후행 작업은 뒤따르는 작업이에요. 항목은
**후행 작업** 쪽에 놓이고, 그 `targetId`가 선행 작업을 가리켜요.

```ts
import type { TaskDependency } from '@jaeungkim/gantt-chart';

// 이건 후행 작업인 "build"에 놓여요. build는 design이 끝나기를 기다린다는 뜻이에요.
const dependencies: TaskDependency[] = [{ targetId: 'design', type: 'FS' }];
```

**지연(lag).** 링크에 붙는 부호 있는 오프셋이고, 하루 단위 정수로 세요 — `workingCalendar`가 켜져
있으면 근무일, 아니면 달력일이에요. 양수면 선행 작업 뒤로 그만큼 기다리고, 음수면 둘이 겹쳐요. 리드는
음수 지연이지 별도 필드가 아니에요.

**베이스라인(baseline).** 계획 시점의 스냅샷이에요. `baselineStart`와 `baselineEnd`로 주고, 실제 막대
아래에 얇은 막대로 그려져요. 데이터가 바뀔 때만 움직여요. 실제 막대를 끌면 제자리에 있는 베이스라인
위를 미끄러져 지나가요. [일정 계산](scheduling)을 참고해요.

## 일정을 가리키는 단어

**근무일 달력(working calendar).** 어떤 날을 셀지 정하는 규칙이에요. `workingCalendar`가 꺼져 있으면
모든 달력일을 세요. 켜져 있으면 기간, 지연, 여유(slack), 전파를 셀 때 주말과 `holidays`를 건너뛰고,
놓은 막대는 다음 근무일에 붙어요. 화면에서 막대는 여전히 주말을 가로질러요. 그 날들을 세지 않을
뿐이에요. 무엇이 바뀌고 무엇이 바뀌지 않는지는 [일정 계산](scheduling)이 정확히 말해줘요.

**일정 정책(scheduling policy).** 막대를 끌거나 크기를 바꿀 때 그 뒤로 이어지는 모든 것에 벌어지는 일이에요.
`schedulingPolicy`는 후행 작업을 그대로 두거나, 끊어진 링크를 뒤로 밀거나, 모든 간격을 그대로 유지하는
것 중에서 골라요 — [일정 계산](scheduling)을 참고해요.

**여유(slack).** 작업이 얼마나 밀릴 수 있는지예요. **총 여유(total slack)**는 프로젝트 종료가 움직이기
전까지 감당할 수 있는 밀림이에요. **자유 여유(free slack)**는 어떤 후행 작업의 가장 이른 시작이
움직이기 전까지 감당할 수 있는 밀림이에요. 둘 다 `criticalPath`가 켜져 있을 때만 계산돼요.

**임계 경로(critical path).** 총 여유가 없는 작업들의 사슬이고, 이게 늦어지면 프로젝트 종료가
움직여요. 진행률 100%인 작업은 절대 여기에 들어가지 않아요 — 규칙과 화살표에 미치는 영향은
[일정 계산](scheduling)에 있어요.

## sequence는 순서를, parentId는 중첩을 정해요

둘은 독립된 필드고, 서로를 맞춰 주는 장치는 없어요.

`sequence`는 계층 여부와 상관없이 언제나 **행 순서**를 정해요. 점으로 이어진 문자열이고, 구간별로
숫자로 비교해요 — 비교 규칙은 [작업 데이터](task-data)가 소유해요.

`parentId`는 **중첩**을 정하는데, `hierarchy` prop이 켜져 있을 때만 그래요. 꺼져 있으면 들여쓰기는
`sequence`의 점 개수에서 읽어요. 그렇다고 `parentId`가 죽어 있는 건 아니에요. 계층이 켜져 있든 꺼져
있든 작업을 지우면 그 하위 트리 전체가 함께 지워져요 — [키보드와 스크린 리더](accessibility)를
참고해요.

작업 세 개를 볼게요. `Audit`은 `Phase 1`의 자식이지만 최상위 `sequence`를 갖고 있어요.

```text
task      sequence   parentId      hierarchy off      hierarchy on
Phase 1   '1'        null          Phase 1            Phase 1
Design    '1.1'      'phase-1'       Design             Design
Audit     '3'        'phase-1'     Audit                Audit
```

행 순서는 두 열에서 같아요. 둘 다 `sequence`를 읽으니까요. 움직이는 건 들여쓰기뿐이에요.

둘이 서로 맞는 건 관례지 규칙이 아니에요. 부모보다 위로 정렬되는 `sequence`를 가진 자식은 부모 위에,
들여쓰기된 채로, 아무 경고 없이 그려져요. 차트가 `sequence`를 대신 고쳐 쓰는 건 행을 재정렬할
때뿐이에요 — [행 재정렬](reordering)을 참고해요.

## 행은 작업이 아니에요

`GanttRow.tasks`는 배열이고, 길이는 0, 1, 또는 그 이상이에요.

| 행 | `tasks.length` | 언제 |
|---|---|---|
| 일반 행 | 1 | 보통의 경우 |
| 레인 행 | 2 이상 | 같은 그룹 안에서 `lane`을 공유하고 시간이 겹치지 않는 작업들 |
| 그룹 헤더 행 | 0 | `groupBy` 값 하나마다 하나 |

그래서 `lane`이나 `groupBy`가 끼는 순간 "세 번째 행"과 "세 번째 작업"은 서로 다른 말이 돼요.
`row.tasks[0]`을 읽는 코드는 그 행의 첫 번째 작업을 읽는 것이지, 행 자체를 읽는 게 아니에요. 행 모델과
그 id, ARIA 번호 매기기는 [그룹과 스윔레인](grouping)과 [`GanttRow`](ref/grouping)가 소유해요.

> [!NOTE]
> 소스에 있는 `lane` 필드의 doc 주석은 이걸 스윔레인이라고 불러요. 이 문서는 두 단어를 구분해요.
> 스윔레인은 `groupBy`가 만들어 내는 행 밴드예요. 레인은 여러 작업을 한 행에 담은 것이에요. 둘은
> 독립된 장치고, 서로 겹쳐서 쓸 수 있어요.

## 어떤 단어가 prop을 켜야 하는지

위 어휘의 절반은 무언가를 켜기 전까지 아무것도 가리키지 않아요.

| 개념 | 필요한 것 | 기본값 |
|---|---|---|
| 요약 행, 롤업, 하위 트리 끌기, 작업 행 접기 | `hierarchy` | `false` |
| 그룹 헤더 행, 스윔레인 | `groupBy` | 설정 없음 |
| 레인 행 | 작업 두 개 이상에 붙은 `lane` 값 | prop 없음 |
| 여유, 임계 경로, `duration` | `criticalPath` | `false` |
| 달력일 대신 근무일로 세기 | `workingCalendar` | `false` |
| 끌어 옮긴 막대가 후행 작업을 움직이기 | `schedulingPolicy` | `'off'` |
| `lag`가 효과를 갖기 | `schedulingPolicy` 또는 `criticalPath` | 둘 다 꺼짐 |
| 베이스라인 막대 | 없음 — 작업에 `baselineStart`만 있으면 돼요 | 항상 켜짐 |

그중 둘이 사람들을 헷갈리게 해요. `schedulingPolicy`도 `criticalPath`도 켜지 않은 차트에서 `lag`는
죽은 값이에요. `lag: 5`인 링크는 `lag: 0`인 링크와 똑같이 그려져요. 베이스라인은 반대예요. 끄는 prop이
없어서, `baselineStart`를 가진 작업은 무조건 하나를 그려요.

## 한계

어휘는 그 뒤에 있는 동작보다 넓어요. 아래가 그 빈틈이고, 호스트 앱에 남는 몫이에요.

- **여기 어떤 단어도 검증을 뜻하지 않아요.** `Task`에는 스키마도 런타임 타입 검사도 없어요. id 중복
  검사도, 날짜 파싱 검사도, 입력 진행률 범위 검사도 없어요. 잘못된 데이터는 조용히 망가지고,
  `sequence`가 없으면 렌더 도중에 예외가 나요. `id`가 같은 작업 둘은 행을 각각 그리지만, id로 찾는 모든
  조회는 — 트리, 의존성 그래프, 롤업 — 그중 마지막 하나만 남겨요. 각 필드가 잘못됐을 때 무슨 일이
  생기는지는 [작업 데이터](task-data)가 나열해요.
- **차트는 데이터를 소유하지 않아요.** `tasks` prop을 그리고, 모든 편집을 `onTasksChange`로 넘겨요.
  저장, 낙관적 업데이트, 서버 왕복은 호스트 앱의 몫이에요. 새 작업을 그리는 것도 초안을 제안할 뿐이고,
  `id`, `parentId`, `sequence`는 호스트가 만들어요. [작업 편집](editing)을 참고해요.
- **리소스, 비용, 공수 모델은 없어요.** 작업에는 담당자, 소유자, 예산 필드가 없어요. 작업 객체에 원하는
  속성을 붙여 그걸로 그룹을 지을 수는 있어요. 다만 타입이 없고, `tasks` 비교에도 포함돼요 —
  [작업 데이터](task-data)가 그 비교를 설명해요.
- **차트 하나에 달력 하나예요.** 작업별 근무일 달력도, 작업별 시간대도 없어요. 모든 날짜는 UTC예요.
- **베이스라인은 그려진 스냅샷이지 비교가 아니에요.** 베이스라인과 실제 날짜의 차이를 계산하는 건
  아무것도 없어요. 숫자가 필요하면 호스트가 그 계산을 해요.
- **행은 레이아웃 API가 아니에요.** 행 높이를 정하거나, 작업이 없는 그룹을 억지로 만들거나, 그룹을 다른
  그룹 안에 넣을 수 없어요.
- **작업이 정확히 하나가 아닌 행이 있으면 행 재정렬이 꺼져요.** `groupBy` 헤더 하나, 또는 작업 둘을
  담은 레인 행 하나면 차트의 모든 행에서 끌기가 조용히 꺼져요. [행 재정렬](reordering)을 참고해요.
