누군가 막대를 잡아 사흘 뒤로 밀고 손을 떼요. 누르고 떼는 그 사이에 차트는 네 가지를 정해요. 이
작업을 편집해도 되는지, 얼마나 멀리 갈 수 있는지, 어디에 놓이는지, 그리고 호스트 앱에 무엇을
알릴지예요. 포인터 제스처 네 개가 작업 데이터를 써요. 다섯 번째는 빈 행 공간에 범위를 그리지만
아무것도 쓰지 않아요.

## 네 가지 제스처

| 제스처 | 시작하는 법 | 쓰는 값 |
|---|---|---|
| 이동 | 가장자리 영역을 벗어난 막대 위에서 누르기 | `startDate`와 `endDate` |
| 왼쪽 크기 조절 | 막대의 왼쪽 가장자리 영역 안에서 누르기 | `startDate` |
| 오른쪽 크기 조절 | 막대의 오른쪽 가장자리 영역 안에서 누르기 | `endDate` |
| 진행률 | 진행률 핸들 위에서 누르기 | `progress` |

네 가지 모두 기본으로 켜져 있어요. 최소한의 연결은 `tasks` 배열과 `onTasksChange` 핸들러예요.

```tsx
// src/App.tsx
import { useState } from 'react';
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const initial: Task[] = [
  {
    id: 'design',
    name: 'Design',
    startDate: '2026-03-02T00:00:00Z',
    endDate: '2026-03-06T00:00:00Z',
    parentId: null,
    sequence: '1',
    progress: 40,
  },
  {
    id: 'build',
    name: 'Build',
    startDate: '2026-03-09T00:00:00Z',
    endDate: '2026-03-20T00:00:00Z',
    parentId: null,
    sequence: '2',
    progress: 0,
  },
];

export function App() {
  const [tasks, setTasks] = useState<Task[]>(initial);
  return <ReactGanttChart tasks={tasks} onTasksChange={setTasks} />;
}
```

커밋되는 제스처는 정확히 한 번의 `onTasksChange` 호출을 만들고, 배열 전체를 실어 보내요. 제스처가
하위 트리 전체를 옮겼거나 후행 작업(successor) 사슬을 밀어냈을 때도 마찬가지예요. 막대를 움직일
만큼 이동하지 못한 제스처는 아무것도 커밋하지 않고 아무것도 호출하지 않아요.

포인터를 누르고 있는 동안에는 아무것도 기록되지 않아요. 움직이는 것처럼 보이는 막대는 데이터와
따로 보관되는 픽셀 오프셋이고, 배열은 손을 뗄 때만 바뀌어요.

### 가장자리 영역이 있는 곳

가장자리 영역은 마우스에서 8px, 터치나 펜에서 44px 너비예요. 이 페이지에서 펜은 전부 터치로
취급해요.

이 영역은 그만한 너비가 되는 막대에만 있어요. 마우스는 렌더링 너비 24px, 터치나 펜은 132px이
필요해요. 그보다 좁으면 막대 전체가 이동 핸들이 되고 크기를 조절할 곳은 없어요. 132px은 분기
배율에서 약 16.5일, 연 배율에서 약 33일이에요. 그래서 작업은 작아 보이기 한참 전에 터치용 크기
조절 가장자리를 잃어요.

가장자리 영역은 이동 영역보다 먼저 검사해요. 그래서 `allowMove: false`와 `allowResize: true`를
가진 작업은 가장자리에서는 크기가 조절되고 가운데에서는 아무 일도 하지 않아요.

### 진행률 드래그

퍼센트는 막대의 렌더링된 사각형 안에서 포인터가 놓인 위치예요. 0-100으로 제한하고 정수 퍼센트로
반올림해요. 포인터 경로에는 단계 크기가 없어요.

값은 포인터가 움직일 때만 샘플링해요. 핸들을 누르고 움직이지 않은 채 떼면 아무것도 바뀌지 않아요.

취소될 때 두 제스처가 갈라져요. 브라우저가 도중에 취소한 진행률 드래그는 마지막 값을 커밋해요.
같은 방식으로 취소된 막대 이동이나 크기 조절은 되돌아가고 아무것도 쓰지 않아요.

### 짧은 드래그는 클릭이에요

포인터가 드래그 한 단계의 절반을 가기 전까지 드래그는 아무것도 커밋하지 않아요. 그 아래에서는
제스처가 기록 없이 끝나고, 뒤따르는 클릭은 그대로 `onTaskClick`에 도달해요. 막대가 한 단계만큼
움직이고 나면 드래그를 끝내는 클릭은 삼켜져요. 클릭 콜백 자체는
[이벤트와 취소 가능한 변경](events)을 참고하세요.

## 드래그가 맞춰지는 단위

드래그는 고정된 격자선에 스냅되지 않아요. 차트는 포인터가 간 거리를 드래그 단계의 정수 배로
반올림해요. 그런 다음 그 단계 수를 작업의 원래 날짜에 더해요.

09:37에 시작하는 작업은 월 배율에서 나흘을 끌어도 여전히 09:37에 시작해요. 시각은 모든 드래그에서
살아남아요. 막대를 자정이나 눈금 경계에 맞추는 장치는 없어요.

| 배율 | 드래그 한 단계 | 첫 단계까지 필요한 포인터 이동 |
|---|---|---|
| `hour` | 15분 | 15px |
| `day` | 1시간 | 16px |
| `week` | 6시간 | 27px |
| `month` | 1일 | 16px |
| `quarter` | 3일 | 12px |
| `year` | 7일 | 14px |

단계 수는 반올림하므로 포인터가 반 단계만큼 움직이면 막대가 다음 단계로 뛰어요. 배율별 전체 설정은
[타임라인](timeline)에 있어요.

배율은 제스처가 시작될 때 확정돼요. 드래그 도중에 배율을 바꿔도 진행 중인 제스처의 단위는 다시
계산되지 않아요.

크기 조절은 항상 최소 한 드래그 단계의 너비를 남겨요. 미리보기뿐 아니라 단계 수 자체가 제한되므로,
크기 조절이 시작일보다 앞선 종료일을 커밋하는 일은 없어요. 이미 한 단계보다 좁은 막대에서는 같은
제한이 반대로 작용해서 막대를 넓혀요.

근무일 달력을 설정하면 끌고 있는 가장자리가 다음 근무일로 한 번 더 스냅돼요. 이동은 양쪽 끝을
함께 스냅해서 막대 길이를 유지해요. [스케줄링](scheduling)을 참고하세요.

## 누가 무엇을 편집할 수 있나요

모든 권한은 작업마다 따로, 네 단계를 거쳐 결정돼요. 값을 가진 첫 단계가 이기고, 그 아래는 아예
보지 않아요.

| 순위 | 설정 | 범위 | 이기는 쪽 |
|---|---|---|---|
| 1 | 작업의 `allowMove` / `allowResize` / `allowProgressChange` | 작업 하나, 권한 하나 | 없음 |
| 2 | 작업의 `readOnly` | 작업 하나, 모든 권한 | 1순위 |
| 3 | 차트의 `allowMove` / `allowResize` / `allowProgressChange` prop | 모든 작업, 권한 하나 | 1-2순위 |
| 4 | 차트의 `readOnly` prop | 모든 작업, 모든 권한 | 1-3순위 |
| 5 | 아무것도 설정하지 않음 | - | - |

5순위는 제스처가 허용된다는 뜻이에요. 어디에도 명시적인 `true` 기본값은 없어요. 관찰되는 기본값은
"무언가 막지 않는 한 허용"이에요.

거꾸로 알기 쉬운 결과가 둘 있어요. 작업의 `readOnly: true`는 차트의 관대한 `allowMove` prop을
이겨요. 2순위가 3순위보다 위에 있기 때문이에요. 그리고 작업 자신의 `allowMove: true`는 두
`readOnly` 설정을 모두 뚫어요. 1순위가 모든 것보다 위에 있기 때문이에요.

`minDate`와 `maxDate`는 더 짧은 자체 사슬을 따라요. 작업에 값이 있으면 그 값, 없으면 차트의
값이에요. 양쪽 끝은 각각 따로 결정되므로, 작업이 하한은 자신에게서 상한은 차트에서 가져올 수
있어요.

막힌 제스처는 실패하는 제스처가 아니에요. 드래그가 아예 시작되지 않고, 누르는 동작이 아무 일도
하지 않아요. 어포던스도 함께 사라져요. 크기를 조절할 수 없는 막대는 크기 조절 그립을 숨기고,
진행률이 고정된 막대는 핸들을 숨겨요. 진행률 채움은 읽기 전용 표시로 계속 보여요. 전체 타입은
[`GanttInteractionConfig`](ref/interaction-config)에 있어요.

### 어떤 플래그로도 되돌릴 수 없는 두 규칙

이 둘은 결정 사슬보다 앞에서 적용돼요. 그래서 어느 수준에서 어떤 플래그를 조합해도 다시 켤 수
없어요.

1. **마일스톤은 절대 크기를 조절할 수 없어요.** 조절할 길이가 없어요.
2. **요약 행은 절대 크기를 조절할 수 없고 진행률도 끌 수 없어요.** 양쪽 끝과 퍼센트가 자식에서
   집계되므로, 편집해도 다음 렌더링에서 곧바로 되돌아가요.

요약 행을 이동하는 것은 여전히 허용되고, 하위 트리 전체를 함께 데려가요. 스케줄링 엔진이 관여하지
않고도 작업 하나보다 많은 날짜를 쓰는 유일한 제스처예요.

요약 행은 `hierarchy`가 켜져 있을 때만 있으므로, 두 번째 규칙은 평평한 차트에는 해당하지 않아요.
[작업 목록과 계층](task-list)을 참고하세요. 요약 행에 `readOnly`를 설정하면 이동까지 포함해
완전히 잠겨요.

### 잠긴 차트에 편집 가능한 막대 하나

차트의 `readOnly`는 4순위예요. 그래서 작업 하나가 다시 편집을 허용할 수 있어요.

```tsx
// src/ReviewBoard.tsx
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const tasks: Task[] = [
  {
    id: 'plan',
    name: 'Plan',
    startDate: '2026-03-02T00:00:00Z',
    endDate: '2026-03-06T00:00:00Z',
    parentId: null,
    sequence: '1',
  },
  {
    id: 'review',
    name: 'Review',
    startDate: '2026-03-09T00:00:00Z',
    endDate: '2026-03-13T00:00:00Z',
    parentId: null,
    sequence: '2',
    // 1순위 - 아래 차트의 readOnly를 이겨요
    allowMove: true,
    allowResize: true,
  },
];

export function ReviewBoard({ onChange }: { onChange: (tasks: Task[]) => void }) {
  return <ReactGanttChart tasks={tasks} readOnly onTasksChange={onChange} />;
}
```

같은 형태가 더 좁은 경우도 덮어요. `readOnly: true`와 `allowProgressChange: true`를 함께 가진
작업은 이동하거나 크기를 조절할 수 없어요. 그래도 진행률 핸들은 여전히 끌려요.

## 드래그 경계

`minDate`와 `maxDate`는 막대를 한 구간 안에 가둬요. 둘 다 UTC ISO 문자열을 받고, 시간대가 없는
문자열은 UTC 벽시계로 읽혀요. `minDate="2026-03-01"`은 로컬 자정이 아니라 UTC 자정이에요.

경계에서 막대가 어떻게 움직이는지는 제스처에 따라 달라요.

- **왼쪽 크기 조절.** 시작일을 구간 안으로 제한한 다음, 종료일보다 최소 한 드래그 단계 앞에 있도록
  뒤로 당겨요.
- **오른쪽 크기 조절.** 종료일을 구간 안으로 제한한 다음, 시작일보다 최소 한 드래그 단계 뒤에
  있도록 밀어내요.
- **이동.** 양쪽 끝이 함께 움직이고 막대는 길이를 유지해요. 막대가 자기 구간보다 길면 `minDate`가
  이기고 막대가 `maxDate` 밖으로 삐져나와요.

막대는 경계를 넘었다가 튕겨 돌아오지 않고 경계에서 눈에 띄게 멈춰요. 제한된 날짜에서 픽셀 오프셋을
매 프레임 다시 재기 때문이에요. `onTasksChange`에 넘어가는 날짜는 경계값 그 자체예요.

요약 행을 이동하면 하위 트리 전체에 공통 델타 하나가 적용되고, 움직이는 작업 중 가장 빡빡한 경계가
이겨요. 그래서 자손의 `maxDate`가 부모의 드래그를 멈춰요. 델타는 요청한 방향을 넘어서지 않아요.
그래서 이미 구간 밖에 있는 작업은 안으로 끌려 들어가지 않고 더 움직이기를 거부해요.

한 단계 최소 너비는 경계 다음에 적용돼요. 그래서 구간을 이미 지나친 막대도 접히지 않고 유효한
막대로 남아요.

근무일 스냅은 제한보다 먼저 실행돼요. 그래서 경계에 붙은 막대가 근무일이 아닌 날에 놓일 수 있어요.

경계는 막대 이동과 크기 조절만 다뤄요. 진행률 드래그, 작업 그리기 제스처, 자동 재스케줄링 연쇄,
행 순서 변경은 경계를 읽지 않아요. `schedulingPolicy`가 밀어낸 후행 작업은 자기 `maxDate` 밖에
놓일 수 있어요.

## 터치

마우스로 누르면 제스처가 곧바로 시작돼요. 터치나 펜은 막대 위에서 400ms 동안 눌러야 드래그가
시작돼요.

기다리는 동안 손가락은 10px까지 흔들려도 괜찮아요. 흔들린 정도는 처음 닿은 지점에서의 가로 거리와
세로 거리를 더해서 재요. 그래서 가로 6px 세로 6px는 12px이 되고, 화면에서는 8.5px인데도 누름이
취소돼요.

누름이 드래그로 넘어가기 전까지 막대는 페이지의 다른 부분처럼 타임라인과 함께 스크롤돼요. 빽빽한
차트를 쓸어 넘기는 동작이 실수로 드래그가 되지 않고 스크롤이 되는 이유예요. 드래그가 시작되고 나면
제스처가 끝날 때까지 터치 스크롤이 억제돼요.

드래그는 손가락이 처음 닿은 자리가 아니라 멈춰 있던 자리에서 시작해요. 대기 중인 드래그 시작을
취소하는 것은 네 가지예요.

| 원인 | 보통 무엇인지 |
|---|---|
| 10px를 넘는 흔들림 | 누름이 아니라 쓸어 넘기기 |
| 400ms 전에 손 떼기 | 탭 |
| 브라우저가 포인터를 취소함 | 시스템 제스처가 넘겨받음 |
| 행이 언마운트됨 | 손가락 아래에서 행이 화면 밖으로 스크롤됨 |

막대는 주 포인터의 왼쪽 버튼에만 반응해요. 두 번째 손가락과 오른쪽 클릭은 아무것도 준비되기 전에
버려져요. 그래서 제스처를 시작하지도 않고 대기 중인 제스처를 취소하지도 않아요. 진행률 핸들에는
그 보호 장치가 없어요.

호버 상태가 없는 기기에서 그 핸들은 10px 점이고, 히트 영역은 44px이에요. 드러낼 호버가 없으니
계속 보여요.

## 뷰포트 가장자리에서의 자동 스크롤

`autoScrollOnDrag`는 기본값이 `true`예요. 정확히 `false`일 때만 꺼져요.

막대 이동이나 크기 조절 중에 포인터가 타임라인 뷰포트의 왼쪽이나 오른쪽 가장자리에서 48px 안으로
들어오면 작동해요. 왼쪽 가장자리는 작업 목록 창을 지난 타임라인 자체의 가장자리예요. 그래서 48px은
윈도우가 아니라 작업 목록 창이 끝나는 지점부터 재요. 창 위로 다시 끌면 영역에 못 미친 게 아니라
가장자리를 지난 것이라, 최대 속도로 왼쪽으로 스크롤해요.

속도는 영역 경계에서 0으로 시작해 가장자리에서 프레임당 22px까지 선형으로 올라가고, 거기서 상한에
걸려요. 타임라인이 좁으면 영역이 뷰포트 너비의 절반으로 줄어들어서 두 영역이 겹치지 않아요.

스크롤되는 프레임마다 마지막으로 알려진 포인터 위치에서 이동이 다시 적용돼요. 포인터를 가장자리에
가만히 두어도 드래그는 계속 나아가요.

제스처가 버려지면 자동 스크롤이 되돌려지고 뷰포트가 시작하던 자리로 부드럽게 돌아가요. 취소된
드래그, 거부된 드래그, 한 단계도 가지 못한 드롭이 여기에 해당해요. 커밋된 드롭은 뷰포트를 스크롤된
자리에 그대로 둬요.

자동 스크롤은 막대 이동과 크기 조절에만 있어요. 가장자리 근처에서 진행률을 끌거나 작업을 그려도
아무 일도 일어나지 않아요.

## 새 작업 그리기

타임라인의 빈 행 공간을 누르고, 옆으로 끌고, 떼세요. 점선 고스트가 포인터를 따라오고, 손을 떼면
차트가 그려진 범위를 호스트 앱에 넘겨요.

누름은 막대나 화살표나 핸들이 아니라 빈 콘텐츠에 닿아야 해요. 마우스는 곧바로 그리기를 시작하고,
터치와 펜은 막대 드래그와 같은 400ms 길게 누르기가 필요해요.

가로 거리만 따져요. 행은 누르는 순간에 고정되므로, 대각선으로 끌어도 시작한 행에 그려요. 4px보다
짧은 드래그는 아무것도 제안하지 않아요.

`Escape`는 진행 중인 그리기를 취소해요. 막대나 진행률 드래그에는 아무 영향이 없어요.

### 그린 범위는 드래그 단계가 아니라 눈금에 맞춰져요

이 페이지에서 스냅 단위가 다른 유일한 곳이에요. 그린 범위는 현재 배율의 눈금 단위까지 바깥으로
넓어져요.

| 배율 | 그린 범위가 맞춰지는 단위 |
|---|---|
| `hour` | 시간 |
| `day` | 시간 |
| `week` | 일 |
| `month` | 일 |
| `quarter` | 월 |
| `year` | 월 |

그래서 연 배율에서 막대는 7일 단위로 끌리지만 그리기는 한 달 단위예요. 눈금 하나 안에 머무는
범위도 눈금 하나 길이로 나와요.

드래그 경계는 적용되지 않아요. 그린 범위는 `minDate`보다 앞에서 시작할 수 있어요.

### 초안, 그리고 차트가 그것으로 하는 일

아무것도 하지 않아요. 차트는 작업을 만들지 않고, 배열을 쓰지 않고, `onTasksChange`를 발생시키지
않아요. 초안을 담아 `onTaskCreate`를 호출하고 거기서 멈춰요. 새 행은 호스트 앱이 작업을 만들어 새
`tasks` 배열을 다시 넘겨줄 때만 나타나요.

`GanttTaskDraft`에는 필드가 셋 있어요. 배율에 맞춰진 UTC ISO 문자열인 `startDate`와 `endDate`,
그리고 범위를 그린 행의 작업 id인 `rowTaskId`예요. `rowTaskId`는 그룹 헤더 행과 마지막 행 아래에서
`null`이에요. 작업 여러 개를 담은 스윔레인 행에서는 첫 작업의 id만 담겨요.
[그룹과 스윔레인](grouping)을 참고하세요. 전체 타입은 [`GanttTaskDraft`](ref/changes)에
있어요.

```tsx
// src/PlanBoard.tsx
import { useState } from 'react';
import {
  ReactGanttChart,
  type GanttTaskDraft,
  type Task,
} from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

export function PlanBoard({ initial }: { initial: Task[] }) {
  const [tasks, setTasks] = useState<Task[]>(initial);

  const handleTaskCreate = ({ startDate, endDate, rowTaskId }: GanttTaskDraft) => {
    const name = window.prompt('Task name');
    if (!name) return; // 아무것도 추가되지 않아요 - 차트는 스스로 아무것도 추가하지 않아요

    setTasks((current) => [
      ...current,
      {
        id: crypto.randomUUID(),
        name,
        startDate, // UTC ISO, 현재 배율의 눈금 단위에 맞춰진 값
        endDate,
        parentId: rowTaskId, // 그룹 헤더 행에서는 null
        sequence: `${current.length + 1}`,
      },
    ]);
  };

  return (
    <ReactGanttChart
      tasks={tasks}
      onTasksChange={setTasks}
      onTaskCreate={handleTaskCreate}
    />
  );
}
```

### 그리기 끄기

`allowTaskCreate`는 차트 전체에 걸려요. 두 단계만 거쳐 결정돼요. 자기 값, 그다음 `!readOnly`예요.
`Task`에는 `allowTaskCreate` 필드가 없고, 거기에 넣어도 무시돼요.

> [!IMPORTANT]
> 이 제스처에는 `onTaskCreate`도 필요해요. 이 콜백이 없으면 `allowTaskCreate`가 무엇이든 십자선
> 커서도, 고스트도, 제스처 자체도 없어요. `allowTaskCreate`만으로는 아무 일도 하지 않아요.

작업이 하나도 없는 차트에서도 그리기에 닿을 수 없어요. 그릴 행이 없기 때문이에요.

## 한계

포인터 편집은 기존 작업의 날짜와 진행률을 써요. 나머지는 다른 곳에 있거나, 호스트 앱이 직접 해야
해요.

- **차트는 작업을 만들지 않아요.** 그리기는 초안을 제안하고, 결정은 호스트 앱이 해요. 포인터로
  작업을 지우지도 않아요. 삭제는 키보드 계층에만 있어요.
- **그린 작업은 거부할 수 없어요.** `onBeforeTaskChange`는 이동, 크기 조절, 진행률 변경을 다루고,
  `onTaskCreate`에는 거부 경로가 없어요.
  [이벤트와 취소 가능한 변경](events)을 참고하세요.
- **막대를 다른 행으로 끌 수 없어요.** 세로 방향 막대 드래그는 없어요. 행의 부모나 위치를 바꾸는
  것은 [행 순서 변경](reordering)이에요.
- **다중 선택 드래그는 없어요.** 한 번에 정확히 막대 하나만 잡혀요. 하위 트리를 데려가는 요약 행이
  유일한 다중 작업 드래그예요.
- **드래그 경계는 스케줄링 제약이 아니에요.** 재스케줄링 연쇄는 이를 완전히 무시해요.
  [스케줄링](scheduling)을 참고하세요.
- **자정이나 눈금에 맞춰지는 것은 없어요.** 드래그는 상대적인 단계 이동이라 원래 시각이 그대로
  보존돼요. 근무일 스냅이 유일한 예외인데, 이것도 하루 단위로 옮기고 시각은 건드리지 않아요.
- **저장은 호스트 앱의 몫이에요.** `onTasksChange`는 배열을 넘겨주고 그것이 `tasks` prop으로
  돌아오기를 기대해요. 아무것도 저장하지 않고 아무 곳에도 보내지 않아요.
- **검증도 호스트 앱의 몫이에요.** 차트는 자기 경계와 최소 막대 길이만 지키고 그 외에는 아무것도
  하지 않아요. 업무 규칙은 `onBeforeTaskChange`에 두세요.
- **의존성 화살표 그리기는 별개의 제스처예요.** 자체 권한 플래그를 가져요.
  [의존성](dependencies)을 참고하세요.
- **드래그 한 단계보다 좁은 막대는 가장자리를 잡으면 넓어져요.** 축소 제한이 더 내줄 것이 없어서,
  첫 포인터 움직임이 잡은 방향으로 한 단계를 더해요. 이동 거리가 없는데도 그대로 커밋돼요.
  마우스에서는 렌더링 너비 24px과 드래그 한 단계 사이에서 이 상황에 닿아요. `week` 배율에서
  24-53px, `day`와 `month`에서 24-31px, `hour`에서 24-29px, `year`에서 24-27px이에요. 터치는
  가장자리가 생기기까지 132px이 필요하니 여기에 걸리지 않아요.
- **진행률 핸들은 막대보다 보호가 약해요.** 주 포인터 검사도 왼쪽 버튼 검사도 없어서 오른쪽 버튼으로
  눌러도 준비돼요. 포인터 id로 거르지도 않아서, 두 번째 손가락의 움직임이 이미 실행 중인 제스처의
  퍼센트를 덮어써요.

이동, 크기 조절, 진행률에는 각각 키보드 대응이 있어요. 같은 권한 사슬과 같은 드래그 경계를 따라요.
키 매핑은 [키보드와 스크린 리더](accessibility)에 있어요. 빈 행 공간에 새 작업을 그리는 데는
키보드 대응이 없고, 의존성 화살표 그리기와 행 순서 변경도 마찬가지예요.

다음: [의존성](dependencies)에서는 막대 두 개를 잇는 방법과, 핸들러에 닿기 전에 차트가 거부하는
것을 다뤄요.
