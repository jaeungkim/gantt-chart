`GanttInteractionConfig` is the chart-wide half of the interaction settings: seven capability flags,
one blanket `readOnly`, and two drag bounds. The type is exported from the package root, but the
chart takes these ten fields as flat props and assembles the object itself — there is no
`interaction` prop.

```ts
import type { GanttInteractionConfig } from '@jaeungkim/gantt-chart';
```

## GanttInteractionConfig

```ts title="src/shared/task.ts"
/** Chart-wide interaction settings - every gesture is allowed by default (task creation also needs `onTaskCreate`), and a task's own field of the same name wins. */
export interface GanttInteractionConfig {
  readOnly?: boolean;
  allowMove?: boolean;
  allowResize?: boolean;
  allowProgressChange?: boolean;
  allowLinkCreate?: boolean;
  allowLinkDelete?: boolean;
  allowTaskCreate?: boolean;
  /** Turns row reordering on - opt-in (default false). */
  allowReorder?: boolean;
  minDate?: string;
  maxDate?: string;
}
```

| Field | Type | Default | Meaning |
|---|---|---|---|
| `readOnly` | `boolean` | `undefined` | Blocks every gesture on every task, and leaves the detail panel's built-in fields as plain text. Any capability flag set at either level beats it — except the panel's **Name**, which reads only the `readOnly` rungs and so stays plain text whatever the capability flags say. |
| `allowMove` | `boolean` | `undefined` | Dragging a bar along the timeline. |
| `allowResize` | `boolean` | `undefined` | Dragging either edge of a bar. It also decides whether the detail panel's **Start** and **End** are editable date inputs. |
| `allowProgressChange` | `boolean` | `undefined` | Dragging the progress handle. It also decides whether the detail panel's **Progress** is an editable number input. |
| `allowLinkCreate` | `boolean` | `undefined` | Starting a dependency drag from a bar's handle. |
| `allowLinkDelete` | `boolean` | `undefined` | Selecting and deleting a dependency arrow. |
| `allowTaskCreate` | `boolean` | `undefined` | Proposing a new task — the **Add task** button, `addTask()` and the drawn range. Chart-wide only. |
| `allowReorder` | `boolean` | `undefined` | Dragging a task-list row to a new position or a new parent, and the keyboard bindings that do the same. |
| `minDate` | `string` | `undefined` | Earliest date any bar may be dragged to, as a UTC ISO string. A date typed into the detail panel is clamped to it too. |
| `maxDate` | `string` | `undefined` | Latest date any bar may be dragged to, as a UTC ISO string. A date typed into the detail panel is clamped to it too. |

Every field unset means every gesture is allowed and there are no drag bounds, with two exceptions.
`allowTaskCreate` also needs an `onTaskCreate` callback — see [Task creation](#task-creation) below.
`allowReorder` is not permissive by default at all — see
[canReorder is not on the chain](#canreorder-is-not-on-the-chain).

The ten props of the same names on `GanttProps` feed this object; see
[GanttProps](props). The per-task fields that override it are on
[Task and task types](task).

## Capability resolution

Each of the six per-task capabilities is resolved by an internal function,
`resolveTaskInteraction`. It is **not exported** from the package root — the resolution order is
documented here because it decides what the chart does, not because it is callable.

```ts title="src/shared/task.ts"
// Precedence: `task.allowX` > `task.readOnly` > `config.allowX` > `config.readOnly` > allowed.
// Summary rows are never resizable and have no draggable progress - both roll up from children.
// Reordering is the exception: its floor is `false`, so only an explicit flag turns it on.
export function resolveTaskInteraction(
  task: Pick<
    Task,
    | 'readOnly'
    | 'allowMove'
    | 'allowResize'
    | 'allowProgressChange'
    | 'allowLinkCreate'
    | 'allowLinkDelete'
    | 'allowReorder'
    | 'minDate'
    | 'maxDate'
  > & { isSummary?: boolean },
  config: GanttInteractionConfig = NO_INTERACTION_CONFIG
): ResolvedTaskInteraction {
  const resolve = (
    taskFlag: boolean | undefined,
    configFlag: boolean | undefined
  ): boolean => {
    if (taskFlag !== undefined) return taskFlag;
    if (task.readOnly !== undefined) return !task.readOnly;
    if (configFlag !== undefined) return configFlag;
    return !config.readOnly;
  };

  const canReorder =
    task.allowReorder ??
    (task.readOnly === true ? false : (config.allowReorder ?? false));

  const derived = task.isSummary === true;

  return {
    canMove: resolve(task.allowMove, config.allowMove),
    canResize:
      !derived &&
      resolve(task.allowResize, config.allowResize),
    canChangeProgress:
      !derived &&
      resolve(task.allowProgressChange, config.allowProgressChange),
    canCreateLink: resolve(task.allowLinkCreate, config.allowLinkCreate),
    canDeleteLink: resolve(task.allowLinkDelete, config.allowLinkDelete),
    canReorder,
    minDate: task.minDate ?? config.minDate,
    maxDate: task.maxDate ?? config.maxDate,
  };
}
```

The order below is what five of the six run. `canReorder` runs a shorter chain of its own, in
[canReorder is not on the chain](#canreorder-is-not-on-the-chain).

The order, most specific first:

1. `task.allowX` — if the task carries its own flag for this capability, that value is the answer.
2. `task.readOnly` — if set, the answer is its negation.
3. `config.allowX` — the chart-wide flag for this capability.
4. `config.readOnly` — the answer is its negation. Unset reads as `false`, so an untouched chart allows the gesture.

`—` in the table below means the field is `undefined`.

| `task.allowX` | `task.readOnly` | `config.allowX` | `config.readOnly` | Result | Decided by |
|---|---|---|---|---|---|
| `true` | any | any | any | allowed | 1 |
| `false` | any | any | any | blocked | 1 |
| — | `true` | any | any | blocked | 2 |
| — | `false` | any | any | allowed | 2 |
| — | — | `true` | any | allowed | 3 |
| — | — | `false` | any | blocked | 3 |
| — | — | — | `true` | blocked | 4 |
| — | — | — | `false` | allowed | 4 |
| — | — | — | — | allowed | 4 |

The ladder in one snippet — the chart is frozen, and one task's own flag re-opens one gesture:

```tsx title="Frozen chart, one live progress handle"
<ReactGanttChart
  readOnly
  tasks={[
    {
      id: 'design',
      name: 'Design',
      startDate: '2026-03-02',
      endDate: '2026-03-06',
      parentId: null,
      sequence: '1',
    },
    {
      id: 'build',
      name: 'Build',
      startDate: '2026-03-09',
      endDate: '2026-03-20',
      parentId: null,
      sequence: '2',
      progress: 40,
      allowProgressChange: true,
    },
  ]}
/>
```

`allowProgressChange` on the second task decides at rung 1, so its progress handle still drags.
Every other gesture on both tasks falls to rung 4, where `readOnly` blocks it.

### The six capabilities

Five of them read one pair of fields through the chain above, then the structural mask in the last
column is `&&`-ed in front of the result. `canReorder` reads its pair through the shorter chain
described under the table.

| Resolved capability | `Task` field | `GanttInteractionConfig` field | Structural mask |
|---|---|---|---|
| `canMove` | `allowMove` | `allowMove` | none |
| `canResize` | `allowResize` | `allowResize` | `!isSummary` |
| `canChangeProgress` | `allowProgressChange` | `allowProgressChange` | `!isSummary` |
| `canCreateLink` | `allowLinkCreate` | `allowLinkCreate` | none |
| `canDeleteLink` | `allowLinkDelete` | `allowLinkDelete` | none |
| `canReorder` | `allowReorder` | `allowReorder` | none |

The resolver returns them in a `ResolvedTaskInteraction`. This type is **not exported** from the
package root either; it is reproduced here because the field names appear in the source and in
this table.

```ts title="src/shared/task.ts"
interface ResolvedTaskInteraction {
  canMove: boolean;
  canResize: boolean;
  canChangeProgress: boolean;
  canCreateLink: boolean;
  canDeleteLink: boolean;
  canReorder: boolean;
  minDate?: string;
  maxDate?: string;
}
```

### canReorder is not on the chain

Reordering is opt-in, so its chain bottoms out at `false` rather than at `!config.readOnly`.

```ts title="src/shared/task.ts"
const canReorder =
  task.allowReorder ??
  (task.readOnly === true ? false : (config.allowReorder ?? false));
```

`config.readOnly` is never read. A frozen chart and an untouched one both refuse to reorder, and
only an explicit `allowReorder` at either level turns it on. The two upper rungs are unchanged: a
task's own flag wins, and a task frozen by its own `readOnly` cannot be dragged by the chart-wide
flag.

| `task.allowReorder` | `task.readOnly` | `config.allowReorder` | Result |
|---|---|---|---|
| `true` | any | any | allowed |
| `false` | any | any | blocked |
| — | `true` | any | blocked |
| — | `false` or — | `true` | allowed |
| — | `false` or — | `false` | blocked |
| — | `false` or — | — | blocked |

### Drag bounds

`minDate` and `maxDate` do not use the chain. They are nullish-coalesced, one level deep:

```ts title="src/shared/task.ts"
minDate: task.minDate ?? config.minDate,
maxDate: task.maxDate ?? config.maxDate,
```

A task's own bound replaces the chart's; `readOnly` and the capability flags have no effect on
either. What the bounds clamp during a drag is covered in [Editing tasks](../editing).

### Task creation

Task creation is chart-wide only, so it has its own two-rung resolver — also internal, also
not exported:

```ts title="src/shared/task.ts"
// Chart-wide only - no entry point starts on a task, so there is no per-task rung
export function canCreateTasks(
  config: GanttInteractionConfig = NO_INTERACTION_CONFIG
): boolean {
  return config.allowTaskCreate ?? !config.readOnly;
}
```

| `config.allowTaskCreate` | `config.readOnly` | Result |
|---|---|---|
| `true` | any | allowed |
| `false` | any | blocked |
| — | `true` | blocked |
| — | `false` | allowed |
| — | — | allowed |

`Task` has no `allowTaskCreate` field, so there is no per-task rung. The chart ANDs the result
with the presence of the callback:

```ts title="src/Gantt.tsx"
const canCreateTask = onTaskCreate !== undefined && canCreateTasks(interaction);
```

That one value gates all three entry points: the **Add task** strip is not rendered without it,
`addTask()` returns early, and the drawing gesture is off. So without `onTaskCreate` there is no way
to create a task, whatever the flags say. See [Creating tasks](../task-creation).

## Constraints

One rule is `&&`-ed in front of the resolver's output, so no flag at any level re-enables it.

**A summary row is never resizable and has no draggable progress.** `canResize` and
`canChangeProgress` are both `false` when `isSummary` is `true`, including when the task sets
`allowResize: true` and `allowProgressChange: true`. `canMove` is unaffected — moving a summary
is allowed and carries its whole subtree.

Both values are derived: `rollUpTasks` recomputes a summary's start and end from its children on
every render, and rolls their progress up too unless the summary carries an explicit one — so an
edit here would either be discarded on the next render or freeze a derived value, which is why no
flag re-enables it.

`isSummary` is set only when the `hierarchy` prop is on, so the rule does not apply to a flat chart.
`readOnly` still freezes a summary row entirely.

## Notes

Exported from the package root: `GanttInteractionConfig` (type only).

Not exported, and named on this page only to describe the chart's behaviour:
`resolveTaskInteraction`, `canCreateTasks`, `ResolvedTaskInteraction`, `NO_INTERACTION_CONFIG`.
Do not import them.

The gestures these flags govern are described in [Editing tasks](../editing) and
[Dependencies](../dependencies). The panel fields they gate are in
