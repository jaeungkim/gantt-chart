The chart draws the timeline and nothing around it — no toolbar, no scale picker. So the "today" button, the "fit everything" button and the scale control are all yours to render. None of them is a prop. They go through a ref on the chart.

## The handle

`ReactGanttChart` is wrapped in `forwardRef`. Point a `useRef<GanttHandle>` at it and the ref holds nine members after mount.

```tsx title="src/ChartWithControls.tsx"
import { useRef } from 'react';
import { ReactGanttChart, type GanttHandle, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

export function ChartWithControls({ tasks }: { tasks: Task[] }) {
  const ganttRef = useRef<GanttHandle>(null);

  return (
    <>
      <button onClick={() => ganttRef.current?.scrollToToday()}>Today</button>
      <ReactGanttChart ref={ganttRef} tasks={tasks} />
    </>
  );
}
```

`GanttHandle` extends `GanttScrollApi`, `GanttDetailApi` and `GanttTaskCreateApi`, and adds nothing of its own.

| Member | Signature | What it does |
|---|---|---|
| `scrollToDate` | `(date: string \| Date \| Dayjs, options?: GanttScrollOptions) => void` | Scrolls horizontally to a date |
| `scrollToToday` | `(options?: GanttScrollOptions) => void` | `scrollToDate(dayjs())` |
| `scrollToTask` | `(taskId: string, options?: GanttScrollOptions) => void` | Scrolls to a task's bar, vertically too if the row is off screen |
| `setScale` | `(scale: GanttScaleKey) => void` | Switches the scale, keeping the centre of the timeline where it is |
| `zoomToFit` | `() => void` | Picks the finest scale that shows every task, then pins the project start to the left edge |
| `getScrollElement` | `() => HTMLDivElement \| null` | Hands back the scroll container DOM node |
| `openDetail` | `(taskId: string) => void` | Opens the detail panel on that task |
| `closeDetail` | `() => void` | Closes the detail panel |
| `addTask` | `() => void` | Proposes a new task through `onTaskCreate` |

`GanttScrollApi`, `GanttDetailApi`, `GanttTaskCreateApi`, `GanttScrollOptions` and `GanttHandle` itself are declared in [GanttHandle](ref/handle).

## Scrolling

Every scroll method takes the same options object.

| Option | Values | Default | Rule |
|---|---|---|---|
| `smooth` | `boolean` | animated | The animation is off only for the literal `false`. `undefined` animates |
| `align` | `'start' \| 'center'` | `'center'` | Only the literal `'start'` takes the start branch |

`align: 'start'` puts the target at the left edge of the timeline area. `align: 'center'` centres it in the timeline area, with the pinned task list pane's width subtracted from the viewport width. Both targets are clamped at `0`, so a date near the beginning of the range lands as far left as the chart can go.

```ts
ganttRef.current?.scrollToDate('2026-09-01', { smooth: false, align: 'start' });
ganttRef.current?.scrollToToday();
ganttRef.current?.scrollToTask('task-42');
```

`scrollToDate` and `scrollToToday` move the horizontal axis only. Neither touches `scrollTop`.

The one scroll that needs no ref is the first one: `initialScrollTo="today"` seeds the position once after the first render, described in [The timeline](timeline). Everything after that is the ref's job.

`scrollToTask` moves both axes. Horizontally it targets the bar's left edge under `align: 'start'` and the bar's midpoint otherwise. Vertically it acts only when the row is outside the viewport, and then it centres the row. `align` has no effect on the vertical axis.

Every one of these fails silently. A date outside the rendered range, an unknown task id, and a chart that is not mounted yet all take an early return with no throw and no console output. This is deliberate, so that calling one while data is still loading is safe.

`scrollToTask` searches the rendered rows only. A task under a collapsed parent is not in that list, so the call is a no-op. Expand the row first. Collapse state is covered in [Task list and hierarchy](task-list).

## Changing the scale

The chart renders no scale control, so the picker is yours to build. `setScale` writes the scale and the `onScaleChange` prop reads it back: the signature is in [GanttHandle](ref/handle), and everything else that moves the scale is in [The timeline](timeline).

Make it a native `<select>`. Your app writes the option text, so the labels translate with the rest of your UI, and the platform brings the keyboard, screen-reader and touch behaviour that five hand-rolled buttons would each have to earn.

```tsx title="src/GanttToolbar.tsx"
import { useRef, useState } from 'react';
import {
  ReactGanttChart,
  type GanttHandle,
  type GanttScaleKey,
  type Task,
} from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const SCALES: GanttScaleKey[] = ['day', 'week', 'month', 'quarter', 'year'];

export function GanttToolbar({ tasks }: { tasks: Task[] }) {
  const ganttRef = useRef<GanttHandle>(null);
  const [scale, setScale] = useState<GanttScaleKey>('month');

  return (
    <>
      <div>
        {/* the ref is null until the chart mounts, so every call is optional-chained */}
        <button onClick={() => ganttRef.current?.scrollToToday()}>Today</button>
        <button onClick={() => ganttRef.current?.zoomToFit()}>Fit</button>
        <button onClick={() => ganttRef.current?.openDetail('task-42')}>
          Details for 42
        </button>

        <select
          aria-label="Timeline scale"
          value={scale}
          onChange={(e) => ganttRef.current?.setScale(e.target.value as GanttScaleKey)}
        >
          {SCALES.map((s) => (
            <option key={s} value={s}>{s}</option>
          ))}
        </select>
      </div>

      <ReactGanttChart
        ref={ganttRef}
        tasks={tasks}
        defaultScale="month"
        onScaleChange={setScale}
        showDetail
      />
    </>
  );
}
```

The select never sets its own state. The choice goes into the chart and the chart reports it back, so a change made with the wheel or the keyboard travels the same path and the select follows it. `zoomToFit()` lands on a scale of its own and is reported the same way, so the **Fit** button updates the select without a line of wiring.

The buttons mirror nothing: the methods read the store at the moment they are called. Only the select holds a value, and `onScaleChange` is what keeps it honest.

The row above the chart on the [playground](/playground) is a toolbar of this shape, and every method on this page except `setScale` is a button in the console beside it. `setScale` is the one with no button: the strip's native `<select>` drives it, exactly as above.

## Zooming

`zoomToFit()` reads the earliest `startDate` and the latest `endDate` across the rendered tasks. It then walks the scale ladder from finest to coarsest — `day`, `week`, `month`, `quarter`, `year` — and takes the first scale where the whole span fits in the timeline's width. When nothing fits, it lands on `year`. The earliest date is pinned to the timeline's left edge.

It takes no options. The resulting scroll is always instant, because the anchor is applied by assigning `scrollLeft` directly rather than through `scrollTo({ behavior })`.

The fit is measured against an average px-per-millisecond figure per scale, not against the ticks that will actually be built. That figure is exact for the scales whose ticks are a fixed duration and approximate on `quarter` and `year`, whose ticks follow the calendar — month cells on `quarter`, quarter cells on `year` — so a span that lands within a few percent of the viewport width can pick the neighbouring scale.

It bails out silently with no tasks, with no mounted scroll element, and when the min or max date is not a finite number.

There is no `zoomIn` or `zoomOut` on the handle. Step your own array of the five keys through `setScale`, or leave the stepping to `Ctrl`/`Cmd` + wheel and `Ctrl`/`Cmd` + `ArrowUp`/`ArrowDown`. Both are described in [The timeline](timeline).

`GanttZoomAnchor` is exported from the package, but nothing on the handle accepts one. `setScale` and `zoomToFit` each build their own. It is a type you may see in the surface, not something you can pass.

## The detail panel

Two methods drive the detail panel from outside the chart. `openDetail(taskId)` opens the docked side panel on a task, `closeDetail()` closes it. What the panel is, what turns it on and what it renders live in [Detail panel](detail-panel). This is the ref side of it.

```ts
ganttRef.current?.openDetail('task-42');
ganttRef.current?.closeDetail();
```

Both do nothing while the panel is off, and off is the default: the panel exists only once `renderDetail` or `showDetail` turns it on. So a button wired to `openDetail` needs no guard of its own. It stays inert until the chart has a panel to open and starts working the day you pass a renderer.

`openDetail` ignores an id that names no task, the same silence as `scrollToTask`. It parts company with `scrollToTask` on one point: the id is resolved against every task the chart holds, collapsed rows included, so a task hidden under a collapsed parent still opens its panel. Scrolling is the call that needs a rendered row, which is why the two are worth making together.

`closeDetail()` on an already closed panel does nothing, and fires no `onDetailChange`.

```tsx title="src/ChartWithDetail.tsx"
import { useRef } from 'react';
import { ReactGanttChart, type GanttHandle, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

export function ChartWithDetail({ tasks }: { tasks: Task[] }) {
  const ganttRef = useRef<GanttHandle>(null);

  // scroll first, then open: the panel resolves ids the chart cannot scroll to
  const inspect = (taskId: string) => {
    ganttRef.current?.scrollToTask(taskId);
    ganttRef.current?.openDetail(taskId);
  };

  return (
    <>
      <ul>
        {tasks.map((task) => (
          <li key={task.id}>
            <button onClick={() => inspect(task.id)}>{task.name}</button>
          </li>
        ))}
      </ul>

      <ReactGanttChart ref={ganttRef} tasks={tasks} showDetail />
    </>
  );
}
```

With `showDetail` on, the panel also opens on the click that selects a row and on `Enter` on the focused row, so your button joins the chart's own triggers rather than replacing them. To make your code the only way in, hold `detailTaskId` yourself and set it from the button: a chart click then only reports through `onDetailChange`, and you decide whether to follow it.

`Escape` closes the panel from anywhere, whatever holds focus, and leaves the row selected. There is no global opening key to match it — `Enter` needs a focused row — so a keyboard shortcut of your own is `openDetail` again.

With `detailTaskId` given the chart is controlled, and neither method moves the panel by itself. They report the request through `onDetailChange` and the panel follows when your state does. Without the prop the chart holds the open task itself, both methods act at once, and `onDetailChange` fires all the same.

## Adding a task

`addTask()` is the one member that is about the data rather than the view. It builds the same draft the **Add task** strip under the task list builds — one tick at today, snapped to the current scale — and hands it to `onTaskCreate`.

```tsx
ganttRef.current?.addTask();
```

It writes nothing, exactly like the strip and like a drawn range: the row appears when your handler puts the task in the `tasks` array. Without `onTaskCreate`, or with creation switched off — `allowTaskCreate={false}`, or `readOnly` while `allowTaskCreate` is unset — the call is inert. So a button of yours wired to it needs no guard, the same as one wired to `openDetail`.

It is also what a keyboard shortcut of your own calls. The chart binds no key to task creation.

The draft, and what turns creation off, are in [Creating tasks](task-creation).

## Limits

- **The handle never touches the data.** `addTask()` is the only member that comes near a write, and it only proposes one task: it calls `onTaskCreate` and writes nothing. No method edits, moves or deletes a task, and every change to the tasks goes through the `tasks` prop and `onTasksChange`.
- **There is no vertical scroll API.** Nothing exposes `scrollToRow` or a scroll-position getter beyond `getScrollElement()`, which hands back the raw DOM node for you to drive yourself.
- **No method reports failure.** An out-of-range date, an unknown id, an unknown scale key and a detail call made while the panel is off all look exactly like success from the outside.
- **The handle has no getter for the scale.** `setScale` writes it and `onScaleChange` reports it. Nothing on the ref reads it back, so the current scale lives in your state or nowhere.

The signature and default of every prop named here are in [GanttProps](ref/props).
