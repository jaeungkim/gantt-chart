The chart reports clicks, selection and edits through callbacks. A drag or a keyboard edit is
written to the chart's own copy of the tasks, and `onTasksChange` receives the whole array. This
page lists every callback, what it receives, and the three that can cancel a change.

## Clicks and selection

Four callbacks and one flag cover clicks. The first three are attached to the bar and to the task
list row, so a click in either pane fires the same callback with the same argument.
`onDetailChange` follows them. The click that selects a row also opens the detail panel when the
panel is on.

| Prop | Signature |
|---|---|
| `onTaskClick` | `(task: TaskTransformed, event: React.MouseEvent) => void` |
| `onTaskDoubleClick` | `(task: TaskTransformed, event: React.MouseEvent) => void` |
| `onTaskSelect` | `(task: TaskTransformed \| null) => void` |
| `onDetailChange` | `(task: TaskTransformed \| null) => void` |
| `selectable` | `boolean` |

`TaskTransformed` is the task plus the layout fields the chart computed for it. Its shape is in
[Task and task types](ref/task). The signature and default of every prop named here are in
[GanttProps](ref/props).

```tsx title="src/ProjectGantt.tsx"
import { useState } from 'react';
import {
  ReactGanttChart,
  type Task,
  type TaskTransformed,
} from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

export function ProjectGantt({ initial }: { initial: Task[] }) {
  const [tasks, setTasks] = useState<Task[]>(initial);
  const [inspected, setInspected] = useState<TaskTransformed | null>(null);

  return (
    <>
      <ReactGanttChart
        tasks={tasks}
        onTasksChange={setTasks}
        onTaskClick={(task) => console.log('clicked', task.id)}
        onTaskDoubleClick={(task) => console.log('open editor for', task.id)}
        onTaskSelect={setInspected}
      />
      <aside>{inspected ? inspected.name : 'Nothing selected'}</aside>
    </>
  );
}
```

### Selection defaults

`selectable` has no fixed default. Passing `onTaskSelect` turns selection on, and so does turning
the detail panel on. `selectable` overrides both in either direction.

| `selectable` | `onTaskSelect` | Selection |
|---|---|---|
| omitted | omitted | off, unless the detail panel is on |
| omitted | given | on |
| `true` | omitted | on, highlight only |
| `true` | given | on |
| `false` | given | off, and `onTaskSelect` is never called |

With `selectable={false}` the whole selection path exits before your handler, so `onTaskSelect`
is never called even when it is passed.

The panel describes the selected row, so turning it on turns selection on as well. With
`renderDetail` or `showDetail` given and `selectable` omitted, rows select even though
`onTaskSelect` was never passed. The chart resolves it as
`selectable ?? (detailEnabled ? true : undefined)`, so `selectable={false}` still wins. The panel
keeps opening on a click, with no row highlighted. What turns the panel on is in
[Detail panel](detail-panel).

Inside one click the order is fixed. `onTaskClick` fires first, and the selection changes after
it. `onTaskSelect` fires only when the selected id changes, so clicking a row that is already
selected fires `onTaskClick` and no `onTaskSelect`.

The highlight is a CSS class. The selected row gets `.gantt-grid-row.selected` and the selected
bar gets `.gantt-task-bar.selected`.

### Empty timeline clicks

A click on the timeline background clears the selection and calls `onTaskSelect(null)` when a
task was selected. A second click on the background changes no id and fires nothing. The row
backgrounds and the non-working day shading take no pointer events, so they do not block the
click.

The empty area of the task list pane and the date axis header do not clear the selection. The
clearing handler listens on the timeline body only.

### Clicks after a drag

The browser fires a click after the `pointerup` that ends a drag. On a bar the chart drops that
click, so a finished drag fires no `onTaskClick` and leaves the selection alone. The flag it checks
is set only when the snapped drag step count changed, so a press that never crossed one step is
still a click. Drag steps are per scale and are covered in [Editing tasks](editing).

Task list rows have no such flag. The collapse toggle stops its own click, so expanding a row
never selects it. The reorder grip stops only its `pointerdown`, and the click that follows still
reaches the row. Pressing the grip fires `onTaskClick` and selects the row, whether or not the row
moved.

### Double clicks

The chart has no click count debounce. A double click on a bar fires `onTaskClick` twice and then
`onTaskDoubleClick` once. If single click does real work and double click opens an editor, that
work runs twice before the editor opens.

### Detail panel callbacks

`onDetailChange` fires on every open and every close, in controlled and uncontrolled mode alike,
with the task or `null`. The panel opens on the click that selects the row, so `onTaskClick` fires
first and the panel opens after it. `Enter` or `Space` on a focused row opens it the same way. A
double click fires two `onTaskClick` calls and one `onTaskDoubleClick`, and the panel opens on
the first click.

`Escape`, the panel's close button and a click on the empty timeline all fire
`onDetailChange(null)`. The callback reports gestures and ref calls only, so setting the
`detailTaskId` prop yourself fires nothing. A task removed from `tasks` closes its panel without
firing `onDetailChange`. What opens the panel, `renderDetail` and the controlled `detailTaskId`
are in [Detail panel](detail-panel).

## Gesture commits

A move, a resize and a progress drag commit on `pointerup`. The chart writes the result into its
own copy of the tasks and calls `onTasksChange` once with the whole array, however many tasks the
gesture moved. Dragging a summary bar moves its subtree, and every task in that subtree is in the
array. No callback runs before the write, and none can stop it.

A gesture that never crossed a drag step ends without a write or a callback.

`onTasksChange` receives the array only. The gesture type, the edge and the moved ids are not
included. Diff it against the array you last passed in to find what changed.

Rejecting a change means putting the old data back. The `tasks` prop wins whenever its contents
differ from what the chart holds, so passing back the array you had before the gesture returns
the bar to where it was.

### Optimistic updates

The chart applies the change before your handler runs, so the UI is already updated when you send
the request. If the request fails, pass the previous array back to revert it.

```tsx title="src/ServerBackedGantt.tsx"
import { useState } from 'react';
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

async function save(tasks: Task[]): Promise<void> {
  const response = await fetch('/api/tasks', {
    method: 'PUT',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(tasks),
  });

  if (!response.ok) throw new Error(`save failed: ${response.status}`);
}

export function ServerBackedGantt({ initial }: { initial: Task[] }) {
  const [tasks, setTasks] = useState<Task[]>(initial);
  const [error, setError] = useState<string | null>(null);

  return (
    <>
      {error ? <p role="alert">{error}</p> : null}
      <ReactGanttChart
        tasks={tasks}
        onTasksChange={(next) => {
          // The array the chart is showing right now, before this gesture
          const previous = tasks;

          setError(null);
          setTasks(next);

          save(next).catch(() => {
            setError('Could not reach the server. Your change was undone.');
            // Contents differ from what the chart holds, so the bar goes back
            setTasks(previous);
          });
        }}
      />
    </>
  );
}
```

`onTasksChange` fires once per gesture with the full array, so one request covers the grabbed bar
and its subtree. The chart recognizes the array it just handed you when it comes back as `tasks`,
so the ordinary controlled loop does not overwrite the drag result on screen.

## Edit paths

| Path | Callback | Cancellable |
|---|---|---|
| Move, resize or progress drag | `onTasksChange` | no |
| Keyboard nudge, progress step or delete | `onTasksChange` | no |
| A field edited in the detail panel, or `update()` from `renderDetail` | `onTasksChange` | no |
| Dragging a row to a new slot or parent, or its keyboard equivalent | `onTaskMove`, then `onTasksChange` | yes, sync |
| The **Add task** button, `addTask()` on the ref, or a range drawn below the last row | `onTaskCreate` | n/a, the chart adds nothing itself |
| Drawing a dependency arrow | `onDependencyCreate`, return `false` to cancel | yes, sync |
| Deleting a dependency arrow | `onDependencyDelete`, return `false` to cancel | yes, sync |

The same edits are available from the keyboard. `Alt` with a horizontal arrow moves a bar, `Shift` resizes
it, `+` and `-` step its progress, and `Delete` removes it. Each of those commits straight to the
tasks and fires `onTasksChange`, like the gesture it replaces. To stop an edit before it happens,
turn that gesture off through the permission chain in [Editing tasks](editing). The full key map
is in [Keyboard and screen readers](accessibility).

The detail panel edits the same way. Its built-in fields commit on blur or `Enter`, and a custom
body commits through `update(patch)`. Both write straight to the tasks and fire `onTasksChange`
with the whole array. Which fields take input, and what a refused value does, is in
[Detail panel](detail-panel).

A row move is the exception to that order. `onTaskMove` runs before anything is applied, and returning `false`
drops the move with nothing written. The grip drag and its keyboard equivalent both route through
it. Its payload and the rules a move must pass are in [Reordering rows](reordering).

The three cancelling callbacks are synchronous. The chart reads the return value immediately, so a
promise is truthy and the change commits. Returning a promise from `onDependencyCreate` to ask a
server first does not work. The dependency payloads are in [Dependencies](dependencies).

## Limitations

- Selection is one internal id. There is no multi-select and no `selectedTaskId` prop, so your
  code cannot set the selection, restore it after a remount, or clear it. Track it from
  `onTaskSelect` if you need it outside the chart.
- Context menu, hover and focus have no callback. Right click is not reported. A context menu needs
  your own listener on the chart container, reading `data-task-id` off the event target.
- Dates and progress have no before-change gate. A drag, a keyboard edit or a detail panel edit is
  written before your code runs. A rule that must hold for every edit is enforced after the fact
  in `onTasksChange`. Only dependency changes and row moves run a callback first.
- Undo is your app's job. Passing the old `tasks` array back is the whole mechanism, and nothing
  animates it. The bar is redrawn at the old dates on the next render.
- Drag lifecycle callbacks do not exist. There is no `onDragStart`, `onDragMove` or `onDragEnd`,
  and `onTasksChange` fires at the end of a gesture only.
- Persistence is your app's job. Nothing is stored or sent. `onTasksChange` hands you an array and
  expects it back as the `tasks` prop.
- A progress drag cancelled by the browser commits, while a bar drag cancelled the same way
  reverts. That asymmetry is in [Editing tasks](editing).

## Event summary

| Action | Callback | Cancellable |
|---|---|---|
| Clicks a bar or its row | `onTaskClick`, then `onTaskSelect`, then `onDetailChange` when the panel is on | no |
| Double clicks a bar or its row | `onTaskClick` twice, then `onTaskDoubleClick`. The panel opens on the first click | no |
| Clicks the empty timeline | `onTaskSelect(null)` if something was selected, and `onDetailChange(null)` if the panel was open | no |
| Finishes a drag on a bar | none, the trailing click is dropped | n/a |
| Moves or resizes a bar | `onTasksChange` | no |
| Drags the progress handle | `onTasksChange` | no |
| Edits with the keyboard | `onTasksChange` | no |
| Edits a field in the detail panel | `onTasksChange` | no |
| Drags a row to a new slot or parent | `onTaskMove`, then `onTasksChange` | yes, sync |
| Expands or collapses a parent row | `onCollapsedChange`. See [Task list and hierarchy](task-list). | no |
| Clicks **Add task**, calls `addTask()`, or draws a range below the last row | `onTaskCreate` | n/a, the chart writes nothing |
| Draws a dependency arrow | `onDependencyCreate`, then `onTasksChange` | yes, sync |
| Deletes a dependency arrow | `onDependencyDelete`, then `onTasksChange` | yes, sync |
| Opens or closes the detail panel from `Enter`/`Space`, `Escape`, the close button or the ref | `onDetailChange` | no |
| Changes the scale from the ref, `Ctrl`/`Cmd` + wheel or the keyboard | `onScaleChange`. See [The timeline](timeline). | no |
| Changes the rendered timeline range | `onRangeChange`. See [The timeline](timeline). | no |

Every stats row in the [playground](/playground) console is one of these callbacks firing live.
