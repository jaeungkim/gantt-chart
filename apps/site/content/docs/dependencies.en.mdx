A dependency is an arrow between two bars. The entry is stored on the successor, the task that waits, and its `targetId` holds the predecessor's id. The arrow points at the successor, so `targetId` is not the id at the arrowhead.

This page covers the entry, the four link types, drawing and deleting links, and what the chart does not validate.

## Dependency entries

The entry goes on the task that waits.

```tsx title="src/DependencyExample.tsx"
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const tasks: Task[] = [
  {
    id: 'design',
    name: 'Design',
    startDate: '2025-06-02',
    endDate: '2025-06-05',
    parentId: null,
    sequence: '1',
  },
  {
    id: 'build',
    name: 'Build',
    startDate: '2025-06-05',
    endDate: '2025-06-12',
    parentId: null,
    sequence: '2',
    // Build waits on Design, so the entry sits on Build
    dependencies: [{ targetId: 'design', type: 'FS' }],
  },
];

export function DependencyExample() {
  return <ReactGanttChart tasks={tasks} height={300} />;
}
```

This draws one arrow from Design to Build. `design` has no `dependencies` field. The field types are described in [Task and task types](ref/task).

An entry whose `targetId` matches no task in the array is skipped when arrows are built, with no warning. No other check runs on the data. See [Interaction traps](#interaction-traps).

## Link types

The two letters name the ends the arrow leaves and enters. The first is the predecessor's end and the second is the successor's. Finish is the right edge of a bar and start is the left edge.

`type` is required on every entry and has no default. The four values are listed in [Task and task types](ref/task).

These are the names scheduling tools use, where `FS` means the successor cannot start before the predecessor finishes. The chart does not apply that rule. A link whose dates contradict its type is drawn the same as one whose dates agree.

Arrows render at 45% opacity. Hovering or selecting a task raises every arrow with that task at either end to full opacity.

## Drawing a link

Each bar has two connector dots, one at each end. They are 12px circles placed 18px outside the bar's edges, with a larger invisible hit area.

With a mouse the dots appear when the bar is hovered or selected. On a device without hover they stay faintly visible and pressable.

The dots render only when the task's `allowLinkCreate` resolves to true. The task's own field overrides the chart prop of the same name, in the order [GanttInteractionConfig](ref/interaction-config) describes. `allowLinkDelete` resolves the same way.

Press a dot and drag. The drag starts after the pointer has moved 4px, so a plain click on a dot creates nothing.

Release anywhere on the target's row. The whole row accepts the drop, including the space beside the bar. On a lane row with several bars, the horizontally nearest bar receives the link.

The target is computed from the row model. The chart ignores the element under the pointer, so an overlay in your app cannot intercept the drop.

The dot you pressed sets the first letter of the type and the release point sets the second.

The finish zone is the last 24px of the target bar, capped at a third of its width, plus everything to its right. The rest of the row counts as the start, so a drop outside the finish zone makes `FS`.

| Drag starts at | Released over | Type |
|---|---|---|
| the end dot | the row, outside the finish zone | `FS` |
| the start dot | the row, outside the finish zone | `SS` |
| the end dot | the finish zone | `FF` |
| the start dot | the finish zone | `SF` |

During the drag a dashed line follows the pointer. Over a valid target the line becomes solid and takes the elbow route the committed arrow will use. The two-letter type appears beside it and the receiving dot fills in.

Dragging against a viewport edge scrolls the timeline, so a link can join two bars that do not fit on screen together. `Escape` cancels the drag.

### Rejected targets

While the pointer is over a candidate, the chart validates the pair. On a rejected target the outline and the preview line turn red and the reason appears beside the pointer. Releasing there commits nothing.

| Rejection | Condition | Text shown |
|---|---|---|
| self | the two ids are equal | `Cannot link a task to itself` |
| duplicate | the successor already has an entry whose `targetId` is this predecessor | `These tasks are already linked` |
| cycle | walking the predecessor's own predecessors reaches the successor | `That would create a circular dependency` |

The checks run in the order the table lists.

The duplicate check compares `targetId` only and ignores `type`. An existing link from `design` to `build` of any type blocks a second link between the same ordered pair. The reverse pair is checked by the cycle rule instead.

The three messages are hardcoded English and do not pass through `locale` or `formats`.

A target whose `allowLinkCreate` resolves to false is not a candidate. The row shows no highlight or reason text. Releasing there does nothing.

### The create callback

Every link the drag did not reject reaches `onDependencyCreate`. That includes links across lanes, links onto a summary row, and links whose dates contradict the type.

```tsx title="src/LinkGuard.tsx"
import { useState } from 'react';
import {
  ReactGanttChart,
  type GanttDependencyChange,
  type Task,
} from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

export function LinkGuard({ initial }: { initial: Task[] }) {
  const [tasks, setTasks] = useState<Task[]>(initial);

  return (
    <ReactGanttChart
      tasks={tasks}
      onTasksChange={setTasks}
      onDependencyCreate={(change: GanttDependencyChange) => {
        // Only an exact false aborts
        if (change.type === 'SF') return false;
      }}
      onDependencyDelete={({ predecessorId, successorId }) =>
        window.confirm(`Unlink ${predecessorId} -> ${successorId}?`)
      }
    />
  );
}
```

The return value is compared with `=== false`. `true`, `undefined`, `null` and `0` all commit. A returned `Promise` also commits, because the two callbacks are synchronous and never await it. An async guard resolves after the link is already in the data.

`GanttDependencyChange` has three fields: `predecessorId`, `successorId` and `type`.

A committed link is written into the task array and `onTasksChange` fires with the new array. To undo it, pass the previous array back.

Props and defaults: [GanttProps](ref/props).

## Deleting a link

Each arrow has an invisible 12px wide hit path along its route, rendered only when the successor's `allowLinkDelete` resolves to true. Hovering the path colours the arrow with the accent colour and shows a pointer cursor. The hover colour marks an arrow as deletable.

Pressing the path selects the arrow. A selected arrow takes the accent colour and shows a round delete button, a cross in a circle, at the midpoint between its two endpoints.

While an arrow is selected, these inputs apply.

| Input | Effect |
|---|---|
| `Delete` or `Backspace` | delete the selected link |
| `Escape` | deselect |
| pointerdown anywhere | deselect |

Key presses are ignored while focus is in an `input`, `textarea`, `select` or `contentEditable` element.

`allowLinkDelete` is read on the successor, the task whose `dependencies` array loses the entry. The same field on the predecessor has no effect. When the flag is false the delete returns without a change or a warning.

The removal filters by `targetId` only. If one successor holds two entries with the same predecessor, both arrows select together and one delete removes both.

When a bar cell has keyboard focus and an arrow is selected, `Delete` reaches both handlers. The link is removed and the focused task is deleted, as two separate changes. The task delete key is described in [Keyboard and screen readers](accessibility).

## Interaction traps

`allowLinkCreate: false` on a task blocks links in both directions. The chart reads it on the source when it renders the dots, and again on the target during the drag. The task cannot start a link or receive one.

The self, duplicate and cycle checks run only during a drag. The chart does not validate the `tasks` array, so a self link or a cycle already in the data is drawn as is, with no warning.

The drag check works when the data already contains a cycle. The walk skips ids it has visited, so it terminates and catches new cycles.

A link never moves a bar. A new `FS` link leaves an overlapping successor where it is, and dragging either bar afterwards leaves the other in place.

## Limitations

The chart draws and removes links but does not manage them.

- Link types cannot be edited in place. Changing `FS` to `SS` means rewriting the entry in your `tasks` array.
- Links are not enforced. Adding an `FS` link does not move the successor, and no check runs on the dates afterwards.
- Links have no keyboard path. The connector dots have `tabIndex={-1}` and no key starts a link drag, so an arrow must be selected with a pointer before `Delete` applies to it.
- Arrows select one at a time. There is no multi-select.
- Arrows have no hover tooltip, context menu or label. An arrow is controlled through its hit path and, when selected, its delete button. No other control acts on an arrow.
- Arrow routes are fixed. The elbow is computed from the two endpoints and the type, so an arrow can cross other bars.
- Arrows to hidden tasks are not drawn. A link whose predecessor is filtered out or hidden under a collapsed parent has no arrow, and the entry stays in your data.
- Changing an existing link has no callback. `onDependencyCreate` and `onDependencyDelete` cover creation and deletion.
- Link validation is not exported. A host that wants the same self, duplicate and cycle checks writes them itself.
