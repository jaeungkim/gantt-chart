You render the chart and get a column of unpositioned divs with no colors. The stylesheet is a
separate file, and importing the component does not pull it in. Once it is loaded the chart is
themed by 27 CSS custom properties and one `theme` prop.

Nearly every color, shadow and transition in the chart reads a `--gantt-*` variable; the ones
that do not are named under Limits. There is no theme object in JS and no `tokens` prop. CSS is
the whole mechanism.

## The stylesheet

The package exports the built CSS under its own subpath.

```tsx title="src/main.tsx"
import { ReactGanttChart } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';
```

That subpath resolves to `dist/gantt-chart.css`. The package entry does import the stylesheet,
but the library build emits it as that separate file instead of inlining it, so importing the
component pulls in no styles.

Without the import the chart still mounts and still responds to clicks. It has no styles at all:
no token declarations, no colors, and none of the layout rules. Sticky headers, the bar geometry,
the flex column of the container and the `box-sizing: border-box` the layout math assumes all live
in that file. The result is unreadable rather than merely plain.

`box-sizing` is scoped to `.gantt-container` and its descendants. The library ships no global
reset, so the file is safe to import into an app that has its own.

## The theme prop

`theme` takes `'light'`, `'dark'` or `'system'`. It is optional.

```tsx
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const tasks: Task[] = [
  { id: 'spec', name: 'Spec', parentId: null, sequence: '1',
    startDate: '2026-03-02T00:00:00Z', endDate: '2026-03-06T00:00:00Z' },
];

export function DarkChart() {
  return <ReactGanttChart tasks={tasks} theme="dark" height={480} />;
}
```

The container always ends up with a resolved `data-theme`, which is the only thing the stylesheet
reads. What decides it:

| `theme` | `data-theme` | Decided by |
|---|---|---|
| `'light'` | `"light"` | the prop |
| `'dark'` | `"dark"` | the prop |
| `'system'` | `"light"` / `"dark"` | `prefers-color-scheme` — the OS |
| *(omitted)* | `"light"` / `"dark"` | the host page's `color-scheme` |
| any value, server render and first hydration render | `"light"` | fixed, to avoid a hydration mismatch |

`className` is folded into the class attribute separately and no longer carries any theme meaning.
`className="my-chart"` yields `gantt-container my-chart`; the theme rides on `data-theme` alone, so
a host class named `dark` or `light` no longer fights the prop.

### With no theme prop: the host decides

Omitting `theme` is not the same as `theme="light"`. With no prop the chart follows the page's
`color-scheme`, read off `<html>`:

```css title="your app"
:root { color-scheme: light; }
.dark { color-scheme: dark; }
```

`color-scheme` is the platform's own light/dark signal, it inherits, and every mainstream theme
switch already writes it — `next-themes` sets it on `<html>`, and so do Tailwind and fumadocs
setups built on it. So a chart with no `theme` prop moves with your app's toggle, with no wiring:

```tsx
// The app's own switch already drives this.
<ReactGanttChart tasks={tasks} height={480} />
```

A `MutationObserver` watches `<html>` for `class`, `style` and `data-theme` changes, so flipping
the switch repaints the chart on the next render. No reload, no remount.

If the page's `color-scheme` is `light dark` — or unset, or `normal` — there is no host preference
to follow, so the OS decides. A page that never mentions `color-scheme` reads as light, which is
what such a page is.

### How system is detected

`theme="system"` reads `window.matchMedia('(prefers-color-scheme: dark)')` through
`useSyncExternalStore`, and ignores the host page. It is for a chart that should track the OS even
inside an app whose own theme is pinned. If you want the chart to match the app, leave `theme` out.

The server snapshot is fixed at `"light"`: neither the host's `color-scheme` nor the OS is readable
without a document. A host that themes before paint — `next-themes` injects a blocking script that
does — is already correct on the first client render, so only static HTML shows the light frame.

## The custom properties

All 27 tokens are declared on `.gantt-container`, never on `:root`. On `:root` they would collide
with a host app's own `--background` and `--border`.

20 of them are redefined for dark. The other 7 are shared by both themes and are marked with a
dash below.

### Surface and text

| Token | Light | Dark | Paints |
|---|---|---|---|
| `--gantt-background` | `#fafafa` | `#09090b` | container, grid pane, grid header, top header groups, content area; link-handle and progress-handle fill; tooltip text |
| `--gantt-foreground` | `#18181b` | `#fafafa` | body text, grid cells, top group label, bar tooltip background, and a bar label rendered outside the bar once that bar is hovered, selected or moving |
| `--gantt-muted` | `#f4f4f5` | `#18181b` | bottom header row, row hover and selection, swimlane group rows; the drag readout's labels, which take the tick row's own surface so they blank only the numerals they cover |
| `--gantt-muted-foreground` | `#71717a` | `#a1a1aa` | secondary text (grid header cells, tick labels, group-count pill), a resting bar label rendered outside its bar, bar resize grips, summary-bar end caps, scrollbar thumb hover |
| `--gantt-border` | `#e4e4e7` | `#27272a` | header and grid borders, scrollbar thumb, expander hover fill |
| `--gantt-border-subtle` | `rgba(0, 0, 0, 0.04)` | `rgba(255, 255, 255, 0.04)` | row separators, the line between the two header rows |
| `--gantt-accent` | `#3b82f6` | — | every focus ring, selected-row inset bar, selected or hovered dependency arrow, link handle border, link preview, draw-to-create ghost |

### Progress

| Token | Light | Dark | Paints |
|---|---|---|---|
| `--gantt-progress-bg` | `#8e8e97` | `#6c6c76` | the progress fill inside a bar - a step toward the foreground in both themes, so the filled part reads against the bar without losing the label on top of it |
| `--gantt-progress-handle` | `#52525b` | `#a1a1aa` | the progress handle border; its fill is `--gantt-background` |

### Dependency arrows

| Token | Light | Dark | Paints |
|---|---|---|---|
| `--gantt-arrow` | `#a1a1aa` | `#71717a` | arrow stroke and arrowhead fill |

Arrows rest at 45% opacity so a dense chart is not dominated by its own relationships, and go to full strength when they are selected, hovered, or attached to the hovered or selected task. A selected or hovered arrow also switches to `--gantt-accent`.

### The today line

| Token | Light | Dark | Paints |
|---|---|---|---|
| `--gantt-today-marker` | `#f43f5e` | `#fb7185` | the today line, **and** every invalid-state color: rejected link previews, rejected link targets |

### Non-working days

| Token | Light | Dark | Paints |
|---|---|---|---|
| `--gantt-non-working-bg` | `rgba(0, 0, 0, 0.035)` | `rgba(255, 255, 255, 0.03)` | the shaded weekend and holiday columns |

Which days get shaded is decided by `showNonWorkingDays`, `holidays` and `isNonWorkingDay` — see
[The timeline](timeline).

### The detail panel

| Token | Light | Dark | Paints |
|---|---|---|---|
| `--gantt-detail-width` | `320px` | — | the width of the docked detail panel |

A layout token, not a color one, so the dark blocks leave it alone. The panel is laid out as
`flex: 0 0 var(--gantt-detail-width)` and paints itself from the tokens above — see
[The detail panel](detail-panel).

### Typography and motion

| Token | Light | Dark | Paints |
|---|---|---|---|
| `--gantt-font-sans` | `"Pretendard Variable", Pretendard, -apple-system, BlinkMacSystemFont, "Segoe UI", "Geist", system-ui, sans-serif` | — | the container's `font-family` |
| `--gantt-duration-fast` | `150ms` | — | the bar tooltip's fade-in only; it is duration-only because the transition tokens carry easing, which an `animation` shorthand rejects |
| `--gantt-transition-fast` | `150ms ease` | — | the bar background, the expander chevron's rotation, and the fade of the resize grips, link handles and progress handle |
| `--gantt-transition-normal` | `200ms ease` | — | the box-shadow transition on a bar |

No font is bundled and none is fetched: the stylesheet names Pretendard, so a host that
already serves it gets it, and everyone else falls straight through to the system font. Shipping
it is the host's job — the docs site self-hosts a subsetted variable build through `next/font`.
The base font size is `13px` and is not tokenized.

Under `@media (prefers-reduced-motion: reduce)` every transition and animation inside the
container is forced to `0.01ms`, and `scroll-behavior` to `auto`. That happens whatever the motion
tokens are set to.

## Overriding a token

Write the override on `.gantt-container` and load your stylesheet after the library's. Your rule
and the library's base rule have the same specificity, so source order is what decides.

```css title="app.css"
.gantt-container {
  --gantt-font-sans: "Inter", system-ui, sans-serif;
}
```

That is enough for the 7 tokens the dark block never touches: `--gantt-font-sans`,
`--gantt-accent`, `--gantt-detail-width`, `--gantt-drag-band`, and the three motion tokens. For
the other 20 it is not.

> [!WARNING]
> A one-line override on `.gantt-container` wins in light mode and loses in dark. The library's
> dark rule is `.gantt-container[data-theme="dark"]` at specificity `(0,2,0)`; a plain
> `.gantt-container` rule is `(0,1,0)` and is outranked by it.

A themed token takes two rules, one per theme.

```css title="app.css"
.gantt-container {
  --gantt-bar-bg: #dbeafe;
  --gantt-bar-bg-hover: #bfdbfe;
}

.gantt-container[data-theme="dark"] {
  --gantt-bar-bg: #1e3a5f;
  --gantt-bar-bg-hover: #2b4f7d;
}
```

Setting the tokens on `:root` does nothing. They are declared on `.gantt-container` itself, and a
declaration on the element beats anything inherited from an ancestor.

Source order only settles a tie in specificity, and only between rules in the same cascade layer.
If you import the library's stylesheet into a layer — `@import '@jaeungkim/gantt-chart/style.css'
layer(gantt)` — that layer's order decides instead, and an unlayered rule of yours beats it
outright.

### Scoping to one chart

Pass a `className` and qualify every selector with it. Each qualified selector gains one class
over the library's, so it outranks the block it mirrors.

```tsx
<ReactGanttChart tasks={tasks} className="planning-chart" height={480} />
```

```css title="app.css"
.gantt-container.planning-chart {
  --gantt-bar-bg: #dbeafe;
}

.gantt-container.planning-chart[data-theme="dark"] {
  --gantt-bar-bg: #1e3a5f;
}
```

### Per-task color wins over the tokens

A task's own `color` is written as an inline `--gantt-bar-color` on that bar, which the bar reads
ahead of the theme tokens, so a colored task ignores them entirely — see
[Custom rendering](custom-rendering).

## Remembering the scale

It is not remembered. The scale is per-chart React state, seeded once by `defaultScale`, and a
remount or a reload puts it back to that seed.

Earlier versions persisted it in `sessionStorage` under a key set by `storageKey`. The prop and
the whole storage path are gone. Nothing in the chart writes to storage any more — not the
scale, not drag frames, not the grid width, not collapsed rows, not the scroll position.

`defaultScale` is applied when the store is built rather than in a mount effect, so the first
paint is already at that scale and no invisible stored value can outrank it. To carry a scale
across reloads, store it yourself: take the new value from `onScaleChange`, keep it wherever the
rest of your view state lives, and pass it back as `defaultScale` on the next mount.

The scale keys themselves, and what each one renders, are covered in
[The timeline](timeline). Changing the scale after mount is `setScale` on the ref — see
[Imperative API](imperative-api).

## Limits

What theming does not cover:

- **No JS theme API.** There is no `tokens` prop, no theme object, and no exported default
  palette. `GanttTheme` is the three-value union and nothing else.
- **One color is hardcoded and cannot be themed.** The dependency delete glyph stroke (`#fff`).
- **Geometry is not tokenized.** The top header row is `44px`, the bottom row `28px`, the base
  font size `13px`, and the row height is a JS constant. None of them are variables.
- **`--top-group-inset` is out of reach.** It is declared on `.gantt-top-group`, not on the
  container, and it carries no `--gantt-` prefix. A host cannot set it from `.gantt-container`.
- **The `light` and `dark` classes carry nothing.** Earlier versions also wrote the resolved theme
  as a class on the container. Only `data-theme` is read now; a rule written as
  `.gantt-container.dark { … }` matches nothing the library sets.
- **No provider, and none is needed for the common case.** `theme` is a per-chart prop, but every
  chart that omits it follows the page's `color-scheme`, so one `color-scheme` rule themes them
  all.
- **Nothing is persisted.** Neither the resolved theme nor the scale is stored anywhere. The
  chart no longer touches `sessionStorage` at all.
- **No RTL.** Nothing reads or sets `dir`, and the stylesheet uses physical properties throughout.
- **Nothing is validated.** An unknown `theme` value produces no warning.

What the host app does itself:

- Import `@jaeungkim/gantt-chart/style.css`, and import it before its own stylesheet.
- Repeat every themed override under both of the library's selectors.
- Persist the scale itself, if a reload should keep it — `onScaleChange` out, `defaultScale`
  back in.
- Set `color-scheme` when it flips its own light/dark state, which is what a chart with no `theme`
  prop follows. Pass `theme` explicitly only to override that per chart.
- Reach for a task's `className` when a token cannot express the change — see
  [Custom rendering](custom-rendering).
