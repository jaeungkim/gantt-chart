title: "행 순서 바꾸기"
description: "작업 목록의 행을 새 자리나 새 부모로 끄는 방법, 그 이동이 다시 쓰는 것, 그리고 이동을 거부하는 법"
---

날짜는 맞는데 순서가 틀렸어요. 두 행은 자리를 맞바꿔야 하고, 그중 하나는 다른 부모 밑에 있어야
해요. [작업 편집](editing)의 모든 제스처는 끌 때까지 켜져 있어요. 이 제스처는 켤 때까지 꺼져 있어요.

차트의 `allowReorder`가 모든 행에 대해 켜요.

```tsx
<ReactGanttChart tasks={tasks} onTasksChange={setTasks} allowReorder hierarchy />
```

작업 자신의 `allowReorder`는 여전히 차트의 값을 이기고, 작업의 `readOnly: true`는 이를 막아요.
차트의 `readOnly`는 아예 참조되지 않아요. 순서 바꾸기에는 거슬러 내려갈 허용 기본값이 없기
때문이에요. 전체 결정 과정은 [GanttInteractionConfig](ref/interaction-config)에 있어요.

나타나는 것은 끌 수 있는 행 왼쪽 끝의 그립이고, 호버할 때와 키보드 포커스가 있을 때 보여요.
움직일 수 없는 행은 그 자리에 빈 여백을 들고 있어서 글자가 옆으로 밀리지 않아요. 그립은 행
드래그가 시작되는 유일한 곳이에요. 행의 다른 곳을 누르면 여전히 이전처럼 클릭되고 선택돼요.
손가락은 막대에서와 같은 400ms 동안 그립 위에 머물러야 하고([작업 편집](editing) 참고), `Escape`는
행을 원래 자리에 내려놓아요.

## 놓이는 자리

드롭은 포인터 아래 행의 어디를 지나는지를 읽어요.

| 구역 | 끌던 행이 놓이는 곳 |
|---|---|
| 위쪽 1/4 | 그 행 앞, 형제로 |
| 가운데 1/2 | 그 행 안, 마지막 자식으로 |
| 아래쪽 1/4 | 그 행 뒤, 형제로 |

가운데 구역이 행의 절반이라, 부모 바꾸기가 넓은 표적이고 두 형제 구역이 정밀한 표적이에요. 최상위
행의 형제 구역은 중첩된 행이 최상위로 돌아오는 길이기도 해요.

차트가 거절하는 드롭은 손을 뗄 때 삼켜지는 게 아니라, 포인터가 아직 눌려 있는 동안 거절돼요.
이렇게 거절되어 호스트 앱에 닿지 않는 드롭은 셋이에요. 자기 하위 트리 안에 놓기, `hierarchy`가
꺼진 채로 부모 바꾸기, 그리고 아무것도 바꾸지 않는 드롭이에요.

접힌 행 안으로 놓으면 그 행이 펼쳐져요. 방금 들어간 행이 사라져 보이지 않게요.

## 이동이 다시 쓰는 것

행 순서는 오직 `sequence`에서 나오고, `sequence`는 경로예요. `"2.1"`은 `"2"`의 첫 자식이에요.
`"1.1"`과 `"1.2"` 사이로 정렬되는 문자열은 없으니, 이동은 두 행 사이에 분수 키를 끼울 수 없어요.
대신 번호를 다시 매기고, 새로 쓰는 번호는 이동이 만들어 낸 행 순서, 곧 화면에 보이는 순서에서
그대로 읽어요.

그래서 한 번의 이동은 경로가 바뀐 모든 작업의 `sequence`를, 그리고 옮긴 작업 하나의 `parentId`를
다시 써요. 옮긴 행의 자식들은 여전히 그 행을 가리키고 함께 따라가요. 경로가 그대로인 작업은 객체
동일성까지 유지되므로, 배열을 비교하는 호스트 앱에는 실제로 움직인 것만 보여요. 이 모든 것이 다른
커밋된 제스처와 마찬가지로 배열 전체를 실은 한 번의 `onTasksChange`로 호스트 앱에 도달해요.

## 이동이 바꾸지 않는 것

- **작업의 날짜.** 부모가 바뀌어도 `startDate`와 `endDate`는 그대로예요. 새 부모의 기간에 맞춰
  늘어나거나 잘리지 않아요.
- **막대의 자리** — 요약 행만 예외예요. 요약 행의 시작과 끝은 자식에서 다시 계산되니까, 자식 하나가
  다른 부모로 가면 옛 부모와 새 부모의 막대는 새로 그려져요.
  [작업 목록과 계층](task-list)을 참고하세요.
- **의존성.** 링크는 id로 이어져 있어요. 행이 어디로 가든 화살표는 같은 두 작업을 잇고, 타입도
  방향도 그대로예요.

## 이동 거부하기

`onTaskMove`는 무엇이든 적용되기 전에 실행돼요. `false`를 반환하면 이동이 버려져요. `sequence`는
다시 쓰이지 않고, `onTasksChange`는 발생하지 않고, 행은 있던 자리에 남아요.

전달되는 `GanttTaskMoveChange`는 작업과 이동의 양 끝을 담아요. 있던 자리는 `fromParentId`와
`fromIndex`, 놓인 자리는 `toParentId`와 `toIndex`, 그리고 이제 사이에 앉은 형제들이 `afterId`와
`beforeId`예요. 인덱스 쌍은 인덱스 기반 API에, 형제 쌍은 위치 기반 API에 맞아요. 둘 다 같은
결과에서 읽어 낸 같은 자리라 서로 어긋날 수 없어요. 전체 형태는 [트리 헬퍼](ref/core-tree)에
있어요.

```tsx title="src/PlanBoard.tsx"
import { useState } from 'react';
import {
  ReactGanttChart,
  type GanttTaskMoveChange,
  type Task,
} from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

export function PlanBoard({ initial }: { initial: Task[] }) {
  const [tasks, setTasks] = useState<Task[]>(initial);

  const handleTaskMove = ({ taskId, toParentId, toIndex }: GanttTaskMoveChange) => {
    const previous = tasks;

    // 위치 기반 API라면 대신 { parentId: toParentId, after: afterId }를 보내요
    fetch(`/api/tasks/${taskId}/move`, {
      method: 'PATCH',
      body: JSON.stringify({ parentId: toParentId, index: toIndex }),
    }).catch(() => setTasks(previous)); // 서버가 거절했어요 - 행을 되돌려요
  };

  return (
    <ReactGanttChart
      tasks={tasks}
      onTasksChange={setTasks}
      onTaskMove={handleTaskMove}
      allowReorder
      hierarchy
    />
  );
}
```

`onTaskMove`는 await되지 않아요. 정확히 `false`만 이동을 거부하므로, 프로미스를 반환하는 핸들러는
이미 이동을 통과시킨 거예요. 그것이 위 예제의 형태예요. 적용하고, 보내고, 서버가 거절하면 이전
배열을 되돌려 놓는 거죠.

## 서버가 거절한 이동 되돌리기

되돌리는 데 새 API는 필요 없어요. 차트는 호스트의 `tasks` prop을 진실로 읽으니까, 이전 배열을
그대로 다시 넘기면 되돌아가요. 이건 호스트가 배열을 상태로 들고 있을 때만 가능해요. 리터럴 배열을
넘겨 두고 자기 사본을 추적하게 둔 차트에는 되돌릴 것이 없어요. 서버에 연결한 차트는 controlled로
쓰세요. [작업 데이터](task-data)를 참고하세요.

같은 이동이 키보드에도 있어요. `Alt` + 세로 화살표가 형제 사이에서 옮기고, `Ctrl`/`Cmd` + 가로
화살표가 들여쓰고 내어써요. [키보드와 스크린 리더](accessibility)를 참고하세요.

## 한계

- **작업을 여러 개 얹은 행은 끌 수 없어요.** `lane`을 공유하면 한 행에 작업이 여럿 올라가고,
  그립이 무엇을 옮기라는 것인지 정해지지 않아요. 드롭 대상이 될 수도 없어요.
  [레인](lanes)을 참고하세요.
- **행 안으로 놓으면 항상 자식들 맨 뒤에 놓여요.** 가운데 구역은 덧붙이기예요. 두 자식 사이 자리를
  가리키는 구역은 없어요. 옆에 두고 싶은 자식의 형제로 놓거나, `Alt` + 화살표로 마무리하세요.
- **행 드래그에는 자동 스크롤이 없어요.** `autoScrollOnDrag`는 막대 이동과 크기 조절에만 걸려요.
  그래서 뷰포트 위나 아래 밖의 드롭 대상은 먼저 스크롤해서 보이게 해야 해요.
  [작업 편집](editing)을 참고하세요.

다음: [의존성](dependencies)에서는 막대 두 개를 잇는 방법과, 핸들러에 닿기 전에 차트가 거부하는
것을 다뤄요.
