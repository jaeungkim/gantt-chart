Design hands back a screenshot where blocked tasks are amber and the client's tasks carry a brand
blue. None of that needs a fork, and none of it needs a render prop. The chart takes a color per
task and a class name per task, and those two fields reach every part of a bar you would want to
change. Start with `color`; reach for `className` when the answer is not a color.

## Per-task color

A `Task` carries an optional `color`. Any CSS color value is legal, including `var(--brand)` and
`rgb(255 0 0 / 50%)` — the string is passed through untouched. The rest of the field list is in
[Task data](task-data).

```tsx title="src/App.tsx"
import { useState } from 'react';
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const initial: Task[] = [
  {
    id: 'design',
    name: 'Design',
    startDate: '2026-03-02T00:00:00Z',
    endDate: '2026-03-06T00:00:00Z',
    parentId: null,
    sequence: '1',
    progress: 40,
    color: '#2563eb',
  },
  {
    id: 'build',
    name: 'Build',
    startDate: '2026-03-09T00:00:00Z',
    endDate: '2026-03-20T00:00:00Z',
    parentId: null,
    sequence: '2',
    progress: 0,
    color: 'var(--brand-amber)',
  },
];

export function App() {
  const [tasks, setTasks] = useState<Task[]>(initial);
  return <ReactGanttChart tasks={tasks} onTasksChange={setTasks} />;
}
```

One value colors the whole bar. The chart does not read a second token for the hover shade, the
progress fill or the label; it derives all three from the color you gave, so a colored bar never
mixes in the theme gray. A colored task sets exactly four CSS custom properties, inline on the bar
node.

| Custom property | Value |
|---|---|
| `--gantt-bar-color` | the trimmed `color`, verbatim |
| `--gantt-bar-color-hover` | `color-mix(in srgb, <color> 86%, #000)` |
| `--gantt-progress-color` | `color-mix(in srgb, <color> 62%, #000)` |
| `--gantt-bar-text-color` | `oklch(from <color> clamp(0, (l / 0.5637 - 1) * -infinity, 1) 0 h)` |

The string is trimmed before it is used. A `color` that is `undefined`, `''` or whitespace emits no
properties at all, and that bar renders exactly like an uncolored one.

### Where the four properties are read

Each declaration names the task property first and a theme token as its `var()` fallback.

| Element | Declaration |
|---|---|
| bar background | `var(--gantt-bar-color, var(--gantt-bar-bg))` |
| bar background on hover | `var(--gantt-bar-color-hover, var(--gantt-bar-bg-hover))` |
| summary bar background | `var(--gantt-bar-color, var(--gantt-summary-bg))` |
| summary bar on hover | `var(--gantt-bar-color-hover, var(--gantt-summary-bg-hover))` |
| progress fill | `var(--gantt-progress-color, var(--gantt-progress-bg))` |
| progress fill on a summary bar | `var(--gantt-progress-color, var(--gantt-foreground))` |
| task name inside the bar | `var(--gantt-bar-text-color, var(--gantt-bar-text))` |

A summary bar falls back to the summary token, not the bar token. That is only visible when the
task has no `color`.

### The label color

The last row is the one that is computed rather than mixed. A bar painted `#fde68a` with a label
in the theme's near-white is unreadable, so the label is derived from the color instead of from the
theme: `l` is the color's own lightness, and dividing it by the threshold before multiplying by
`-infinity` collapses it to one end or the other. A pale bar gets a black label, a dark bar a white
one.

The threshold is `0.5637`, which is not arbitrary. It is the OKLab lightness of the relative
luminance where black and white tie on WCAG contrast, so the label is always the higher-contrast of
the two. A higher cut looks reasonable and is not: at `0.7` a Tailwind `#ef4444` bar takes a white
label at 3.76:1 when black would have given 5.58:1.

This is done in CSS, not in JavaScript, because `var(--brand)` is a legal `color` and its lightness
is not knowable until the browser substitutes it. The cost is that the label flip needs relative
color syntax — Chrome 125, Firefox 128, Safari 18 — which is a higher floor than the `color-mix`
the two shades use. Below it the property does not resolve and the label falls back to
`--gantt-bar-text`, which is what every bar did before this existed.

Two edges are worth knowing. The label is pure black or pure white and nothing between, so a bar
sitting near the crossover clears 4.5:1 but not by much — `#2277d3` measures 4.65:1. And the label
sits over the progress fill, which is mixed 62% toward `#000`, so on a light bar the black label
loses contrast across the filled portion.

To opt out, take the specificity: `className` on the task plus a rule of your own.

```css title="src/gantt-overrides.css"
.gantt-task-bar.mine .gantt-task-name {
  color: #fff;
}
```

### When a color wins, and when it does not

The color wins over every theme token in the table above. The token is only a `var()` fallback, so
it is consulted when the task property is absent. Setting `--gantt-bar-bg` chart-wide through the
theme does not override a task's own `color`; see [Theming](theming) for the token list.

The color loses in two places.

- **Anything that is not a background or the label.** The bar's radius, its shadow, the selection
  outline and the dependency arrows all come from theme tokens. `color` changes the seven
  declarations in the table above and nothing else.
- **The task list.** `color` never reaches the left pane. A row in the task list is styled by the
  theme and by `className`.

## className

`className` on a task is put on that task's bar and on its row in the task list. It is appended last
in both class strings, which changes nothing about the cascade — the order of names in a `class`
attribute is not a CSS ordering. A rule of yours wins the way any rule wins: on specificity, or on
coming later at equal specificity. `.gantt-task-bar.blocked` outranks `.gantt-task-bar`, which is
why the example is written that way.

```tsx
const task: Task = {
  id: 'audit',
  name: 'Security audit',
  startDate: '2026-04-06T00:00:00Z',
  endDate: '2026-04-10T00:00:00Z',
  parentId: null,
  sequence: '3',
  className: 'blocked',
};
```

```css title="src/gantt-overrides.css"
.gantt-task-bar.blocked {
  background: repeating-linear-gradient(
    45deg,
    #b45309,
    #b45309 6px,
    #92400e 6px,
    #92400e 12px
  );
}

.gantt-grid-row.blocked .gantt-grid-cell {
  font-style: italic;
}
```

## Replacing a node

There is one render prop, `renderDetail`, and it replaces the body of the docked detail panel. It is
not a styling hook — it exists because the default body shows a name and two dates and no prop adds
a row to it. What opens the panel, its props bag and how to control it are in
[Detail panel](detail-panel); the type is in [Renderers](ref/renderers).

Nothing else in the chart is replaceable. The bar, the tooltip, the header cells, the task-list row,
the group header, the drag readout, the drop indicator and the dependency arrows are all reachable
through CSS and nothing else.

## showTooltip

`showTooltip` defaults to `true`. Setting it to `false` suppresses the hover tooltip and the live
tooltip during a move, a resize and a progress drag.

Turning tooltips off removes the only live-region announcement a pointer drag produces — the gesture
tooltip is that `role="status"` node. Keyboard date edits are announced by a separate live region
that `showTooltip` does not touch; see [Keyboard and screen readers](accessibility).

## Limits

- **Colors are not computed for you.** There is no palette, no color-by-status and no legend. The
  chart reads `task.color` and derives three values from it; every other rule is yours. Map a status
  to a color before you hand the tasks over — `tasks.map((t) => ({ ...t, color: PALETTE[t.status] }))`
  — which is what comparable scheduling libraries expect too.
- **`color-mix` is required for the two shades.** The hover and progress shades are emitted as
  `color-mix(in srgb, …)`, so a browser that cannot parse it resolves neither. `--gantt-bar-color`
  is a plain color and keeps working there.
- **Relative color syntax is required for the label.** It is a higher floor than `color-mix`, and
  below it the label stays `--gantt-bar-text`.
- **The header cell is text.** There is no way to put markup in it. `formats` changes what it says
  and CSS on `.gantt-top-group` and `.gantt-bottom-cell` changes how it looks; that is the whole
  surface. The 44px group row and the 28px tick row are fixed heights.
- **The task list takes no per-task detail.** Its one cell renders `task.name`. Put the rest in the
  [detail panel](detail-panel).

Reach for the two options in that order. `color` handles anything that is a color, and one value
sets all four properties. `className` handles anything the stylesheet can express — a pattern, a
border, a font — and wins over the chart's own rules on specificity.
