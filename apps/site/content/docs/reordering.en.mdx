title: "Reordering rows"
description: "Dragging a row in the task list to a new position or a new parent, the fields a move rewrites, and how to reject one"
---

Row reordering lets a user drag a row in the task list to a new position or a new parent. Unlike
the bar gestures in [Editing tasks](editing), it is off by default. Set `allowReorder` on the chart
to turn it on for every row.

```tsx
<ReactGanttChart tasks={tasks} onTasksChange={setTasks} allowReorder hierarchy />
```

A task's own `allowReorder` overrides the chart's, and `readOnly: true` on a task blocks the move.
The chart's `readOnly` is not consulted, because reordering has no permissive default to fall back
to. [GanttInteractionConfig](ref/interaction-config) describes the full precedence.

Each draggable row shows a grip on its left edge, on hover and on keyboard focus. A row that cannot
move keeps a blank spacer in that slot, so its text does not shift.

A drag starts only on the grip. A press anywhere else in the row clicks and selects the row.
`Escape` cancels the drag and returns the row to its place.

On touch, a finger rests on the grip for the same 400 ms as on a bar. See [Editing tasks](editing).

The same moves are on the keyboard. `Alt` + the vertical arrows moves a row among its siblings, and
`Ctrl`/`Cmd` + the horizontal arrows indents and outdents it. See
[Keyboard and screen readers](accessibility).

## Drop position

The drop position depends on how far down the row under the pointer the release happens.

| Region | Where the dragged row lands |
|---|---|
| top quarter | before that row, as its sibling |
| middle half | inside that row, as its last child |
| bottom quarter | after that row, as its sibling |

The middle region covers half the row, so a move to a new parent is the wide target and the two
sibling regions are the precise ones. A sibling region on a root row also returns a nested row to
the root level.

The chart rejects an invalid drop while the pointer is still down, so the release does nothing.
Three drops are rejected this way and never reach your app: a row dropped inside its own subtree, a
move to a new parent while `hierarchy` is off, and a drop that changes nothing.

A drop into a collapsed row expands it, so the moved row stays visible.

## Rewritten fields

`sequence` alone sets row order. `sequence` is a path, so `"2.1"` is the first child of `"2"`. No
string sorts between `"1.1"` and `"1.2"`, so a move cannot insert a fractional key between two
rows. It renumbers instead, reading the new numbers from the row order on screen after the move.

One move rewrites `sequence` on every task whose path changed, and `parentId` on the moved task
only. The moved row's children point at it and travel with it. Tasks whose path did not change keep
their object identity, so a host that diffs the array sees only the tasks that moved. The result
reaches your app in a single `onTasksChange` carrying the whole array, like any other committed
gesture.

## Unchanged fields

- `startDate` and `endDate` keep their values under a new parent. Nothing is stretched or clipped
  to fit the parent's span.
- A bar keeps its position, except on summary rows. A summary's start and end are recomputed from
  its children, so moving one child out redraws the old parent's bar and the new parent's. See
  [Task list and hierarchy](task-list).
- Links are stored by id, so the arrows join the same two tasks with the same type and direction
  wherever the row lands.

## Rejecting a move

`onTaskMove` runs before the move is applied. Return `false` to drop it. The chart leaves
`sequence` unchanged, skips `onTasksChange`, and keeps the row where it was.

The `GanttTaskMoveChange` it receives carries the task id and both ends of the move.
`fromParentId` and `fromIndex` give the old position, `toParentId` and `toIndex` the new one, and
`afterId` and `beforeId` the siblings on either side of the row after the move. The index pair
suits an index-based API and the sibling pair a position-based one. Both are read from the same
result, so they cannot disagree. [Tree helpers](ref/core-tree) has the full shape.

The example sends each move to a server and reverts it when the request fails.

```tsx title="src/PlanBoard.tsx"
import { useState } from 'react';
import {
  ReactGanttChart,
  type GanttTaskMoveChange,
  type Task,
} from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

export function PlanBoard({ initial }: { initial: Task[] }) {
  const [tasks, setTasks] = useState<Task[]>(initial);

  const handleTaskMove = ({ taskId, toParentId, toIndex }: GanttTaskMoveChange) => {
    const previous = tasks;

    // A position-based API takes { parentId: toParentId, after: afterId } instead
    fetch(`/api/tasks/${taskId}/move`, {
      method: 'PATCH',
      body: JSON.stringify({ parentId: toParentId, index: toIndex }),
    }).catch(() => setTasks(previous)); // the server said no - put the rows back
  };

  return (
    <ReactGanttChart
      tasks={tasks}
      onTasksChange={setTasks}
      onTaskMove={handleTaskMove}
      allowReorder
      hierarchy
    />
  );
}
```

`onTaskMove` is not awaited. Only a literal `false` rejects a move, so a handler that returns a
`Promise` has already allowed it.

## Reverting a move

Undoing a move needs no API of its own. The chart renders from the host's `tasks` prop, so passing
the previous array back reverts the move.

This works only while the host keeps the array in state. A chart given a literal array tracks its
own copy and has nothing to revert to. A chart wired to a server should be controlled. See
[Task data](task-data).

## Limitations

- A row carrying more than one task cannot be dragged. A shared `lane` puts several tasks on one
  row, so the grip has no single task to move. Such a row cannot be a drop target either. See
  [Lanes](lanes).
- A drop into a row always lands last among its children. The middle region appends, and no region
  names a slot between two children. Drop the row as a sibling of the child it belongs next to, or
  finish the placement with `Alt` + the arrows.
- A row drag does not auto-scroll. `autoScrollOnDrag` covers bar moves and resizes only, so a drop
  target outside the viewport has to be scrolled into view first. See [Editing tasks](editing).
