This page defines the terms the rest of the docs use, one word per thing. A row and a task are
different things, and the difference matters when two tasks share a row.

## Chart and host app

The chart is the `<ReactGanttChart>` component that `@jaeungkim/gantt-chart` exports. It renders
the `tasks` prop and calls `onTasksChange` with every edit.

The host app is the application around the chart. It holds the task array, decides what to persist
and applies the array the chart passes to `onTasksChange`. See [Events](events).

## Parts of the chart

<ChartSketch preset="anatomy" />

| Term | Meaning |
|---|---|
| task | One entry in the `tasks` array. |
| bar | The horizontal block drawn for one task. Dragging it is described in [Editing tasks](editing). |
| row | One line of the grid. It holds one task, or several that share a lane. |
| task list | The left pane, listing task names beside the timeline. See [Task list and hierarchy](task-list). |
| timeline | The time axis and everything drawn against it. See [The timeline](timeline). |
| scale | The unit the timeline is drawn in, one of `day`, `week`, `month`, `quarter` or `year`. See [The timeline](timeline). |
| tick | One cell of the lower header row. The time one tick covers depends on the scale. |
| drag step | The distance one snap of a bar drag moves it. The scale sets it, one hour at `day` and 28 days at `year`. See [Editing tasks](editing). |
| drag readout | The dates a live drag writes into the tick cells where its moving edges land, over a tint the width of the bar. A move writes both ends. A resize writes only the end it moves. See [Editing tasks](editing). |
| summary row | A task with children under `parentId`, when `hierarchy` is on. Its dates come from the children. See [Task list and hierarchy](task-list). |
| roll-up | The dates and progress a summary row takes from its children. See [Task list and hierarchy](task-list). |
| lane | The `lane` field, which places several tasks side by side on one row. See [Lanes](lanes). |
| detail panel | The pane docked beside the chart that shows one task. See [Detail panel](detail-panel). |
| treegrid | The `role="treegrid"` element that holds the task list and the timeline as one grid, with one tab stop inside it. See [Keyboard and screen readers](accessibility). |

The snippet below uses every term above.

```tsx title="concepts-demo.tsx"
import { useState } from 'react';
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const initialTasks: Task[] = [
  {
    id: 'phase-1',
    name: 'Phase 1',
    startDate: '2026-03-02',
    endDate: '2026-03-20',
    parentId: null,
    sequence: '1',
  },
  {
    id: 'design',
    name: 'Design',
    startDate: '2026-03-02',
    endDate: '2026-03-06',
    parentId: 'phase-1',
    sequence: '1.1',
    lane: 'Ana',
  },
  {
    id: 'build',
    name: 'Build',
    startDate: '2026-03-09',
    endDate: '2026-03-20',
    parentId: 'phase-1',
    sequence: '1.2',
    lane: 'Ana',
    progress: 40,
    dependencies: [{ targetId: 'design', type: 'FS' }],
  },
  {
    id: 'ship',
    name: 'Ship',
    startDate: '2026-03-23',
    endDate: '2026-03-27',
    parentId: null,
    sequence: '2',
    dependencies: [{ targetId: 'build', type: 'FS' }],
  },
];

export function Demo() {
  const [tasks, setTasks] = useState<Task[]>(initialTasks);

  return (
    <ReactGanttChart
      tasks={tasks}
      onTasksChange={setTasks}
      hierarchy
      workingCalendar
    />
  );
}
```

The snippet renders four tasks on three rows. `design` and `build` share the lane `Ana` without
overlapping, so they are packed onto one row. [Lanes](lanes) describes the packing.

## Data terms

A task is the unit you pass in. The required fields are `id`, `name`, `startDate`, `endDate`,
`parentId` and `sequence`, and every other field is optional. The field table is in
[Task data](task-data) and the type in [Task and task types](ref/task).

A draft is the new task the chart passes to `onTaskCreate`. It carries two dates and no other
field. The host app supplies the `id`, `parentId` and `sequence`. See
[Creating tasks](task-creation).

A dependency is a link between two tasks, of type `FS`, `SS`, `FF` or `SF`. The first letter is the
predecessor's end and the second is the successor's end. See [Dependencies](dependencies).

The predecessor is the earlier task in a link and the successor is the later one. The entry is
stored on the successor, and its `targetId` names the predecessor. The entry below is on `build`,
the successor.

```ts
import type { TaskDependency } from '@jaeungkim/gantt-chart';

// This sits on "build", the successor. It reads: build waits for design to finish.
const dependencies: TaskDependency[] = [{ targetId: 'design', type: 'FS' }];
```

## Working calendar

A working day is a weekday listed in `workingWeekdays` that no `holidays` entry covers.
`workingWeekdays` defaults to Monday to Friday. A holiday is one of those entries, either a
`YYYY-MM-DD` string or an object that also carries a label and a colour.

The working calendar is the rule that reads both. With `workingCalendar` off, a bar stays where the
pointer released it. With it on, a drop on a non-working day moves forward to the next working day.
In both modes, bars span those days on screen and the drag step counts calendar days.
[Working calendar](working-calendar) covers what the setting changes and what it leaves alone. The
shading and the holiday names are described in [The timeline](timeline).

## `sequence` and `parentId`

`sequence` and `parentId` are independent fields. The chart does not reconcile them.

`sequence` sets the row order, with or without hierarchy. It is a dotted string compared segment by
segment as numbers. [Task data](task-data) describes the comparison.

`parentId` sets the nesting, and only when `hierarchy` is on. With `hierarchy` off, indentation
comes from the number of dots in `sequence`. Deleting a task removes its whole subtree with
`hierarchy` on or off, so `parentId` is read in both modes. See
[Keyboard and screen readers](accessibility).

In the table below, `Audit` is a child of `Phase 1` but carries a top-level `sequence`.

| Task | `sequence` | `parentId` | Depth, `hierarchy` off | Depth, `hierarchy` on |
|---|---|---|---|---|
| Phase 1 | `'1'` | `null` | 0 | 0 |
| Design | `'1.1'` | `'phase-1'` | 1 | 1 |
| Audit | `'3'` | `'phase-1'` | 0 | 1 |

Both modes read `sequence` for row order, so the rows come out in the order shown and only the
depth differs.

Agreement between the two fields is a convention. The chart does not enforce it. A child whose
`sequence` sorts above its parent renders above its parent, indented, with no warning. The host app
is responsible for that string on every task it passes in, including tasks drawn on the chart and
tasks it edits.

Row reordering is the exception. With `allowReorder` on, a row can be dragged to a new slot or a
new parent. A move renumbers `sequence` from the resulting row order, so every task whose position
changed gets a new value. `allowReorder` is off by default. See [Reordering rows](reordering).

## Rows and tasks

`GanttRow.tasks` is an array with one or more entries.

| Row | `tasks.length` | When |
|---|---|---|
| ordinary row | 1 | the normal case |
| lane row | 2 or more | tasks that share a `lane` and do not overlap in time |

With `lane` in use, the third row and the third task are different things. Code that reads
`row.tasks[0]` reads the first task on that row, not the row itself. The row model, its ids and its
ARIA numbering are described in [Lanes](lanes) and [GanttRow](ref/rows).

## Terms that need a prop

Some of the terms above describe nothing until a prop is set.

| Term | Needs | Default |
|---|---|---|
| summary row, roll-up, subtree drag, collapsing a task row | `hierarchy` | `false` |
| lane row | a `lane` value on two or more tasks | no prop |
| task list | `showTaskList` | `false` |
| detail panel | `showDetail`, or `renderDetail` on its own | off |
| a drop moving off a non-working day | `workingCalendar` | `false` |

The signature and default of every prop named here are in [GanttProps](ref/props).

## Limitations

The terms above cover more than the chart enforces. The following work stays with the host app.

- `Task` has no schema or runtime type check. The chart does not check id uniqueness, date parsing
  or progress range. Bad data degrades with no warning, and a missing `sequence` throws during
  render. Two tasks with the same `id` both draw a row, but every lookup keyed by id (the tree, the
  dependency graph, the roll-up) keeps only the last one. [Task data](task-data) lists what each
  malformed field does.
- Persistence is the host app's work. The chart renders the `tasks` prop, passes every edit to
  `onTasksChange` and stores nothing itself. Optimistic updates and server round trips are the host
  app's work too. Drawing a new task produces a draft only. See [Creating tasks](task-creation).
- Resources, cost and effort have no model. A task has no assignee, owner or budget field. Custom
  properties on a task object are allowed, but they are untyped and they count toward the `tasks`
  diff. [Task data](task-data) explains that diff.
- The working calendar and the time zone apply to the whole chart, not per task. All dates are UTC.
- Row height is fixed, and every row comes from a task, so an empty row cannot be created.
