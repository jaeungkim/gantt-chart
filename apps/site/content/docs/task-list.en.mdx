title: "Task list and hierarchy"

Bars tell you when something happens and never what it is. The task list is the pane on the left
that puts the task's name beside every row. It is also where `parentId` becomes visible: with
`hierarchy` on, a task that has children is drawn as a summary row whose dates come from those
children instead of from its own record.

## Turning the pane on

The pane is off by default. `showTaskList` turns it on. What it shows is fixed — the one other
switch it has, `showRowNumbers`, is covered below.

| `showTaskList` | Pane |
|---|---|
| omitted | hidden |
| `true` | shown |
| `false` | hidden |

`false` renders the timeline alone. The chart ships no control of its own for hiding the pane —
an end user who should be able to hide it needs a button the host builds, driving `showTaskList`
from its own state. The signature and default of every prop named here are in
[GanttProps](ref/props).

```tsx title="ProjectChart.tsx"
import { ReactGanttChart } from '@jaeungkim/gantt-chart';
import type { Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const tasks: Task[] = [
  { id: 'p1', name: 'Phase 1', parentId: null, sequence: '1',
    startDate: '2025-03-03', endDate: '2025-03-28' },
  { id: 't1', name: 'Design', parentId: 'p1', sequence: '1.1',
    startDate: '2025-03-03', endDate: '2025-03-12', progress: 100 },
  { id: 't2', name: 'Build', parentId: 'p1', sequence: '1.2',
    startDate: '2025-03-12', endDate: '2025-03-28', progress: 40 },
];

export function ProjectChart() {
  return <ReactGanttChart tasks={tasks} showTaskList height={420} />;
}
```

## What the pane shows

Names, in one column, at a starting pane width of 220px.

`showRowNumbers` puts a narrow number column in front of them. It prints `task.sequence`, the
outline path the chart already orders rows by, so the first child of task 2 reads `2.1`. A row
holding a whole lane prints its first task's number and nothing for the rest.

| `showRowNumbers` | Number column |
|---|---|
| omitted | hidden |
| `true` | shown, printing `task.sequence` |
| `false` | hidden |

<GanttDemo preset="rowNumbers" />

The number is the task's own field rather than a count of the rows on screen, so collapsing a
parent renumbers nothing. Reordering a row does change it, because a move rewrites `sequence` —
see [Reordering rows](reordering).

There is no prop for a date column, and adding one is not a planned feature. The bars already
say when a task runs, so a date column beside them repeats the chart and costs the name half the
pane. Everything else about a task — dates in your own format, an owner, a status, a custom
widget — belongs in the detail panel on the right, where there is room for it and where it does
not compete with the name. See [Detail panel](detail-panel).

The header row above them prints nothing. The pane's one header cell is named for screen readers
only — `Task name` — and the number column, drawn inside the tree cell, has no header cell at all.
So the one string the pane renders for the eye is the **Add task** button's label — hardcoded
English, like the rest of the chart's chrome, see [Locale and date formats](i18n).

The pane's foot is the only other thing it renders: an **Add task** strip, present while task
creation is on — that is, while `onTaskCreate` is given and neither `allowTaskCreate: false` nor a
bare `readOnly` switches creation off. Like
the splitter it is rendered outside the treegrid, so the grid keeps its single tab stop and the
button is an ordinary one after it. Clicking it proposes a task; what it proposes, and the other
two ways to propose the same thing, are in [Creating tasks](task-creation).

## The name cell

The one cell is the tree cell — the number, where it is on, is drawn inside it rather than as a
second cell, so the row keeps its single grid cell. Up to six things live inside it:

- a drag grip, while row reordering is on anywhere in the chart — visible only while its row is
  hovered or focused, and replaced by a 20px spacer on rows that cannot move, so the text never
  jogs; see [Reordering rows](reordering);
- the row's `sequence`, with `showRowNumbers` on, ahead of the indent so the column sits at the
  same x whatever the row's depth;
- an indent spacer of `depth * 16` pixels;
- the expander button on an expandable row, or a 20px spacer on every other row;
- the task's name, the one thing the cell exists for — the cell itself carries the same string as a
  native `title` attribute, so a name too long for the pane is still readable on hover;
- a `+N` badge counting the extra tasks when a row holds more than one, which happens with lanes —
  see [Lanes](lanes).

The cell takes the whole pane width, so every pixel the splitter adds goes to the name. A name
that still does not fit is truncated with an ellipsis.

## Resizing the pane

| Control | Behaviour |
|---|---|
| Splitter drag | clamped to 120–800px, width at press plus the pointer's travel since press |
| Splitter double-click | fits the pane to the widest visible row's full name, same clamp |
| Splitter keyboard | `ArrowLeft` / `ArrowRight` step 16px, `Enter` fits like double-click, same clamp |
| Splitter semantics | `role="separator"`, `aria-orientation="vertical"`, label `Resize task list` |

Fit measures the rows on screen. Rows virtualized out of the viewport are not in the DOM, so a
longer name further down does not widen the pane until it is scrolled into view.

The splitter sits outside the treegrid on purpose, so the grid keeps exactly one tab stop and the
splitter is a second, separate one — see [Keyboard and screen readers](accessibility). It is
rendered only while the pane is visible, so
`showTaskList={false}` removes the handle with it.

Pane width is local component state. There is no prop to seed it, no callback when it changes, and
it does not survive a remount.

## Depth from parentId

`hierarchy` is `false` by default. Off, `parentId` is inert for rendering and the indentation you
see comes from the dots in `sequence`.

| | `hierarchy: false` | `hierarchy: true` |
|---|---|---|
| Row order | `sequence` | `sequence` — unchanged |
| Row depth | dot count in `sequence` | steps up the `parentId` chain |
| `isSummary` | never | a task with at least one child |
| Summary dates | raw values render | recomputed from the children |
| Task-row collapse | no expanders, `collapsedIds` inert for task ids | active |

Row order comes from `sequence` in both modes. `parentId` never moves a row. See
[Task data](task-data) for how `sequence` sorts.

## What a summary row's dates are

A summary's `startDate` is the earliest `startDate` among its children. Its `endDate` is the
latest `endDate` among them. The parent's own dates in your data are discarded on every render,
silently.

Roll-up runs deepest first, so a grandchild's move travels up through the parent to the
grandparent. It also runs before the timeline fits its range, so a child
reaching past its parent's stated dates still widens the timeline.

The recomputed values are re-serialized as full UTC ISO strings, which matters if `renderDetail` or
a click callback compares the task it is handed against your source strings — see
[Tree helpers](ref/core-tree).

A parent whose children all carry unparseable dates keeps its own dates and no error is raised.

## What a summary row's progress is

An explicit `progress` on the parent is left alone; only a missing one is rolled up, as a
duration-weighted average of the children, weighted and rounded by
[Tree helpers](ref/core-tree).

## What a summary row cannot do

Resizing and progress dragging are switched off on a summary row, and no per-task flag re-enables
them — see [GanttInteractionConfig](ref/interaction-config).

The progress fill still draws. Only the drag handle is gone.

Moving is not affected. Dragging a summary bar moves its whole subtree by the same delta, bounded
by the intersection of every member's own drag window; see [Editing tasks](editing).

A summary row carries the class `summary` on both its grid row and its bar. The word `summary` is
inserted into its accessible name, between the task name and the date range.

## Collapsing rows

Collapse state is one list of ids, in either controlled or uncontrolled mode.

| Prop | Mode | Rule |
|---|---|---|
| `collapsedIds` | controlled | an array here is what the chart shows, and internal state stops updating |
| `defaultCollapsedIds` | uncontrolled | read once, in the initial state; later changes are ignored |
| `onCollapsedChange` | both | fires on every toggle with the full next array |

The mode switch is `collapsedIds !== undefined`. `null` is not in the prop's type and is not an
opt-out: the pane falls back to the internal list to draw, but stops writing to it, so every
expander freezes while `onCollapsedChange` keeps firing. Passing both props means `collapsedIds`
wins and `defaultCollapsedIds` only seeds state nothing reads.

`onCollapsedChange` fires in controlled and uncontrolled mode alike. It never fires on mount, and
never for `defaultCollapsedIds`. The payload is the whole next array, never a delta: a newly
collapsed id is appended at the end, and an expanded one is filtered out.

Nearly every write is a toggle. The one other writer is a row move: dropping a dragged row into a
collapsed parent expands that parent, so the moved row does not vanish — and `onCollapsedChange`
fires for that expand too. See [Reordering rows](reordering).

> [!WARNING]
> In controlled mode the chart does not collapse anything on its own. It waits for a new
> `collapsedIds` array. Pass `collapsedIds` without handling `onCollapsedChange` and every
> expander looks broken.

A collapsed row stays on screen; its descendants disappear. Collapsing an id with no children is a
silent no-op, and the id stays in the list.

Toggles come from the expander button in the name cell, or from `ArrowRight` / `ArrowLeft` on the
first cell and `Enter` / `Space` anywhere on the row — see
[Keyboard and screen readers](accessibility).

A row that holds several tasks in one lane has the id `a+b`, which matches no task — see
[Lanes](lanes). Whether that row gets an expander is decided by its first task alone, so a summary
sharing a lane gets a toggle that hides nothing.

```tsx title="ProjectChart.tsx"
import { useState } from 'react';
import { ReactGanttChart } from '@jaeungkim/gantt-chart';
import type { Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const tasks: Task[] = [
  { id: 'p1', name: 'Phase 1', parentId: null, sequence: '1',
    startDate: '2025-03-03', endDate: '2025-03-28' },
  { id: 't1', name: 'Design', parentId: 'p1', sequence: '1.1',
    startDate: '2025-03-03', endDate: '2025-03-12', progress: 100 },
  { id: 't2', name: 'Build', parentId: 'p1', sequence: '1.2',
    startDate: '2025-03-12', endDate: '2025-03-28', progress: 40 },
];

export function ProjectChart() {
  const [collapsedIds, setCollapsedIds] = useState<string[]>(['p1']);

  return (
    <ReactGanttChart
      tasks={tasks}
      showTaskList
      hierarchy
      collapsedIds={collapsedIds}
      onCollapsedChange={setCollapsedIds}
      height={420}
    />
  );
}
```

## Edge cases

**A broken `parentId`** — an orphan, a self-reference, an empty string, a cycle — is normalized to
a root before the pane draws it, silently; the rules are in [Tree helpers](ref/core-tree).

**A summary with an explicit `progress`.** It survives, including `0`, because the roll-up only
fills a nullish value. It is not clamped on the way through, so a stored `250` stays `250` on the
task `renderDetail` and the click callbacks receive, while the bar draws at 100%. The progress
handle stays hidden either way.

**Duplicate `id` values.** Nothing dedupes them. The duplicate is pushed into its parent's child
list twice and counted twice in the roll-up.

There is no depth cap. A chain twenty-five levels deep gives its last row a depth of 24, so 384px
of indent.

## Limits

The pane shows the name and cannot be made to show anything else: there is no column API, no
sorting and no filtering. The name cell is a read-only node — there is no inline editor and no
`onCellChange` — and there is no renderer for a grid row. `renderDetail` is the
chart's only render prop, and it draws the detail panel, not a row. The most a row takes from a
task is `className`, in [Styling](styling).

Pane width has no prop and is not persisted. It opens at 220px every time and the splitter is the
only thing that changes it. The layout constants — row height, that starting width, the 120–800
splitter range, the 16px indent — are not exported, so a host cannot import them to match its own
chrome.

The tree does not order rows, and nothing checks that `sequence` agrees with `parentId`. A child
whose `sequence` sorts above its parent renders above it, indented, with wrong ARIA positions and
no warning. Broken parent links are repaired silently: there is no callback, no console message and
no flag on the row.

Roll-up covers `startDate`, `endDate` and a missing `progress`. It does not roll up `color`,
`className` or `dependencies`.

`collapsedIds` and `defaultCollapsedIds` do nothing at all while `hierarchy` is off.

So the host app owns: keeping `sequence` consistent with `parentId`, holding the collapsed list in
state if it wants controlled collapse, persisting pane width itself, building any control that
hides the pane, putting per-task detail in the detail panel, and validating parent links before
render. `buildTaskTree` is exported for that last one — see
[Headless core](headless-core).
