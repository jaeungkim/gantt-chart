API가 작업마다 `blocks` 목록을 줘요. 그 작업을 기다리는 작업들의 목록이죠. 이걸 `dependencies`에 그대로 옮기면 화살표가 전부 반대로 나와요. 필드 이름이 `targetId`라서 화살표가 향하는 쪽 작업처럼 읽히거든요. 하지만 그렇지 않아요. 의존성 항목은 후행 작업(successor)에 놓이고, `targetId`에는 그 작업이 기다리는 선행 작업(predecessor)의 id가 들어가요.

## 링크가 놓이는 자리

기다리는 작업 쪽에 항목 하나를 두면 돼요.

```tsx title="src/DependencyExample.tsx"
import { ReactGanttChart, type Task } from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

const tasks: Task[] = [
  {
    id: 'design',
    name: 'Design',
    startDate: '2025-06-02',
    endDate: '2025-06-05',
    parentId: null,
    sequence: '1',
  },
  {
    id: 'build',
    name: 'Build',
    startDate: '2025-06-05',
    endDate: '2025-06-12',
    parentId: null,
    sequence: '2',
    // Build가 Design을 기다리므로 항목은 Build에 놓여요
    dependencies: [{ targetId: 'design', type: 'FS' }],
  },
];

export function DependencyExample() {
  return <ReactGanttChart tasks={tasks} height={300} />;
}
```

이러면 Design에서 Build로 화살표 하나가 그려져요. `design` 자체에는 `dependencies`가 아예 없어요. 필드 타입은 [Task와 작업 타입](ref/task)에 정리돼 있어요.

`targetId`가 배열의 어떤 작업과도 맞지 않는 항목은 화살표를 만드는 동안 조용히 버려져요. 그 외에는 데이터를 전혀 검사하지 않아요. 이 날카로운 모서리는 [상호작용 함정](#상호작용-함정)에서 다뤄요.

## 네 가지 타입

두 글자는 링크의 양쪽 끝을 가리켜요. 첫 글자는 선행 작업 쪽 끝, 두 번째 글자는 후행 작업 쪽 끝이에요. finish는 막대의 오른쪽 끝, start는 왼쪽 끝이라서, 이 한 쌍이 화살표가 어느 모서리에서 나가고 어느 모서리로 들어가는지를 정해요.

`type`은 모든 항목에 필수고 기본값은 없어요. 네 가지 값은 [Task와 작업 타입](ref/task)에 정리돼 있어요.

이 이름들은 `FS`가 "선행 작업이 끝나기 전에는 후행 작업이 시작될 수 없다"를 뜻하는 일정 관리 도구에서 왔어요. 여기서는 그런 뜻이 전혀 없어요. 두 날짜를 서로 비교하지 않고, 링크를 맞추려고 막대가 움직이는 일도 없어요. 두 날짜가 이름과 어긋나는 링크도 들어맞는 링크와 똑같이 그려져요.

화살표는 45% 불투명도로 그려져요. 작업에 호버하거나 작업을 선택하면 그 작업의 양쪽 끝에 닿는 모든 화살표가 온전한 색으로 올라와요. 그래서 빽빽한 차트에서도 호버 한 번으로 한 작업의 사슬을 골라낼 수 있어요.

## 링크 그리기

막대마다 양쪽 끝에 연결 점이 하나씩, 두 개 달려 있어요. 막대 모서리에서 18px 바깥에 떠 있는 12px 원이고, 더 넓은 보이지 않는 히트 패드를 갖고 있어요. 마우스에서는 막대에 호버하거나 막대를 선택하기 전까지 보이지 않아요. 호버가 없는 기기에서는 대신 옅게 항상 보이고 누를 수 있어요. 그리고 그 작업의 `allowLinkCreate`가 true로 풀릴 때만 렌더링돼요. 작업 자신의 필드를 먼저 보고 그다음 같은 이름의 차트 prop을 보는데, 그 순서는 [GanttInteractionConfig](ref/interaction-config)에 있어요. 아래에 나오는 `allowLinkDelete`도 같은 방식으로 풀려요.

점을 누르고 드래그하세요. 포인터가 4px 움직이기 전에는 아무것도 시작되지 않아요. 그래서 점을 잘못 클릭해도 아무 일이 없어요.

대상 작업의 행 어디에서든 놓으면 돼요. 막대만이 아니라 행 전체가 드롭을 받아요. 막대가 여럿인 레인 행에서는 가로로 가장 가까운 막대가 링크를 가져가요. 대상은 포인터 아래의 요소가 아니라 행 모델에서 계산돼요. 그래서 호스트 앱의 오버레이가 드롭을 삼킬 수 없어요.

타입은 양쪽 끝에서 정해져요. 잡은 점이 첫 글자를 정해요. 놓은 위치가 두 번째 글자를 정하고요. 대상 막대의 마지막 24px과 그 오른쪽 전부를 finish로 쳐요. 막대가 좁으면 그 폭은 막대의 3분의 1로 줄어요. 행의 나머지는 start예요.

| 드래그 시작 지점 | 놓는 위치 | 타입 |
|---|---|---|
| 끝 점 | 행에서 finish 영역 바깥 | `FS` |
| 시작 점 | 행에서 finish 영역 바깥 | `SS` |
| 끝 점 | finish 영역 | `FF` |
| 시작 점 | finish 영역 | `SF` |

느슨하게 놓으면 가장 흔한 경우인 `FS`가 돼요.

드래그하는 동안 점선이 포인터를 따라와요. 유효한 대상 위에 오면 실제로 반영될 화살표의 꺾인 경로로 실선이 되고, 두 글자 타입이 옆에 적히고, 받는 쪽 점이 채워져요. 놓기 전에 읽어 보세요. 뷰포트 가장자리로 드래그하면 타임라인이 스크롤돼요. 그래서 한 화면에 같이 들어오지 않는 두 막대도 이을 수 있어요.

`Escape`를 누르면 드래그가 취소돼요.

### 드래그가 거부하는 것

포인터가 후보 위에 있는 동안 차트는 두 작업의 짝을 검사해요. 거부된 대상의 외곽선이 빨갛게 변하고, 미리보기 선도 함께 빨개지고, 이유가 포인터 옆에 그려져요. 그 상태로 놓아도 아무것도 반영되지 않아요.

| 거부 | 조건 | 표시되는 문구 |
|---|---|---|
| 자기 참조 | 두 id가 같음 | `Cannot link a task to itself` |
| 중복 | 후행 작업에 이 선행 작업을 가리키는 항목이 이미 있음 | `These tasks are already linked` |
| 순환 | 선행 작업의 선행 작업들을 따라가면 후행 작업에 닿음 | `That would create a circular dependency` |

순서는 고정이에요. 자기 참조, 그다음 중복, 그다음 순환이에요.

중복 검사는 `targetId`만 비교해요. `type`은 무시하죠. 그래서 `design → build` 링크가 어떤 타입으로든 이미 있으면 같은 방향의 두 번째 링크는 거부돼요. 반대 방향 짝은 별개의 문제고, 순환 규칙이 따로 검사해요.

세 문구는 영어로 하드코딩돼 있어요. `locale`이나 `formats`를 거치지 않아요.

`allowLinkCreate`가 false로 풀리는 대상은 더 일찍, 더 조용하게 거부돼요. 강조도 되지 않고, 이유 문구도 뜨지 않고, 놓아도 아무 일이 없어요.

### onDependencyCreate에 도달하는 것

드래그가 거부하지 않은 것 전부예요. 레인을 가로지르는 링크, 요약 행으로 향하는 링크, 두 날짜가 서로 완전히 어긋나는 링크까지 모두 콜백에 도착해요.

```tsx title="src/LinkGuard.tsx"
import { useState } from 'react';
import {
  ReactGanttChart,
  type GanttDependencyChange,
  type Task,
} from '@jaeungkim/gantt-chart';
import '@jaeungkim/gantt-chart/style.css';

export function LinkGuard({ initial }: { initial: Task[] }) {
  const [tasks, setTasks] = useState<Task[]>(initial);

  return (
    <ReactGanttChart
      tasks={tasks}
      onTasksChange={setTasks}
      onDependencyCreate={(change: GanttDependencyChange) => {
        // 정확히 false일 때만 중단돼요
        if (change.type === 'SF') return false;
      }}
      onDependencyDelete={({ predecessorId, successorId }) =>
        window.confirm(`Unlink ${predecessorId} -> ${successorId}?`)
      }
    />
  );
}
```

반환값은 `=== false`로 비교돼요. `true`, `undefined`, `null`, `0`은 모두 반영돼요. Promise도 마찬가지예요. 이 두 콜백은 동기 전용이라 반환된 Promise를 기다리지 않아요. 그래서 비동기 가드는 링크가 이미 데이터에 들어간 뒤에 resolve돼요.

`GanttDependencyChange`는 `predecessorId`, `successorId`, `type`만 담고 그 외에는 없어요.

반영된 링크는 작업 배열에 기록되고, `onTasksChange`가 새 배열과 함께 호출돼요. 되돌리려면 갖고 있던 배열을 다시 넘기면 돼요.

여기 나온 prop의 시그니처와 기본값은 [GanttProps](ref/props)에 있어요.

## 링크 삭제

화살표마다 경로를 따라 12px 폭의 보이지 않는 히트 패스가 있어요. 후행 작업의 `allowLinkDelete`가 true로 풀릴 때만 그려져요. 여기에 호버하면 화살표가 강조 색으로 빛나고 포인터 커서가 떠요. 화살표를 지울 수 있다는 유일한 힌트예요. 여기에 포인터를 누르면 화살표가 선택돼요. 선택된 화살표는 강조 색으로 바뀌고, 양 끝점의 중간에 원 안에 X가 든 둥근 삭제 버튼이 생겨요.

화살표가 하나 선택돼 있는 동안에는 이렇게 동작해요.

| 입력 | 동작 |
|---|---|
| `Delete` 또는 `Backspace` | 선택된 링크를 삭제해요 |
| `Escape` | 선택을 해제해요 |
| 아무 곳에서나 포인터 누르기 | 선택을 해제해요 |

포커스가 `input`, `textarea`, `select`, `contentEditable` 요소에 있으면 키 입력은 무시돼요.

권한은 후행 작업의 `allowLinkDelete`를 읽어요. `dependencies` 배열에서 항목이 빠지는 쪽 작업이죠. 선행 작업에 `allowLinkDelete: false`를 줘도 달라지는 건 없어요. 플래그가 false면 삭제는 조용히 반환돼요.

삭제는 `targetId`만으로 걸러 내요. 한 후행 작업에 같은 선행 작업을 가리키는 항목이 둘 있으면 화살표 두 개가 함께 선택돼요. 그리고 한 번의 삭제로 둘 다 사라져요.

막대 셀에 키보드 포커스가 있고 화살표도 선택돼 있으면 `Delete`가 두 핸들러에 동시에 닿아요. 링크가 지워지고 포커스된 작업도 삭제되며, 이건 서로 다른 두 번의 변경이에요. 작업 삭제 키는 [키보드와 스크린 리더](accessibility)에 정리돼 있어요.

## 상호작용 함정

작업에 `allowLinkCreate: false`를 주면 양방향이 모두 막혀요. 점을 렌더링할 때 출발 쪽에서 한 번 읽고, 드래그 중에 드롭 대상에서 또 읽어요. 그래서 그 작업은 링크를 시작할 수도, 받을 수도 없어요.

자기 참조, 중복, 순환 가드는 드래그하는 동안에만 돌아요. 데이터는 전혀 검사되지 않아요. `tasks` 배열에 이미 들어 있는 자기 참조 링크나 순환은 경고 없이 그대로 그려져요. 데이터에 순환이 이미 있어도 드래그 가드는 망가지지 않아요. 탐색이 한 번 본 id를 건너뛰어서 맴돌지 않고 끝나고, 새로 생기는 순환은 여전히 전부 잡아내요.

링크는 막대를 움직이지 않아요. 새 `FS` 링크를 걸어도 겹쳐 있던 후행 작업은 있던 자리에 그대로 남고, 그 뒤에 둘 중 하나를 드래그해도 나머지 하나는 제자리에 있어요.

## 한계

차트는 링크를 그리고 지워요. 관리하지는 않아요.

- **타입 편집 없음.** 화살표가 생긴 뒤에 `FS`를 `SS`로 바꾸려면 `tasks` 배열의 항목을 다시 써야 해요.
- **적용 자체가 없음.** `FS` 링크를 추가해도 후행 작업은 움직이지 않고, 그 뒤에도 날짜를 검사하는 곳이 없어요. 링크는 화살표예요.
- **링크로 가는 키보드 경로 없음.** 연결 점은 `tabIndex={-1}`을 달고 있고, 링크 드래그를 시작하는 키도 없어요. `Delete`가 통하려면 먼저 포인터로 화살표를 선택해야 해요.
- **다중 선택 없음.** 화살표는 한 번에 하나만 선택돼요.
- **화살표의 호버 툴팁, 컨텍스트 메뉴, 라벨 없음.** 쓸 수 있는 건 히트 패스와 선택된 화살표의 삭제 버튼뿐이에요.
- **화살표 경로 재조정 없음.** 꺾임은 양 끝점과 타입만으로 계산돼요. 그래서 화살표가 막대를 거리낌 없이 가로질러요.
- **숨은 작업으로 가는 화살표 없음.** 선행 작업이 필터로 빠졌거나 접힌 부모 아래 숨어 있으면 링크는 그려지지 않아요. 항목은 데이터에 그대로 남아 있어요.
- **"링크 수정" 콜백 없음.** `onDependencyCreate`와 `onDependencyDelete`가 있을 뿐, 그 사이는 없어요.
- **드래그의 가드는 내부용.** 패키지는 링크 검증 함수를 export하지 않아요. 자기 참조, 중복, 순환을 똑같이 검사하려면 호스트 앱에서 직접 짜야 해요.
